# Tessera — правила сопровождения

Текущий проект — предрелизная реализация Tessera v4.0. Не создавать заново. Статус, доказательства и ограничения — [implementation.md](implementation.md); требования — [target-specification-v4.0.md](target-specification-v4.0.md); интерфейс — [ui-specification.md](ui-specification.md); команды — [README.md](README.md). История этапов доступна в Git.

## Git и границы

- По запросу владельца работать в `main` небольшими коммитами, без force-push, переписывания истории, ненужных веток/PR, release tags и публикации.
- Сначала сверять HEAD, дерево и незавершённые изменения. Не сбрасывать чужой WIP. Спецификации не менять без подтверждённой необходимости; ссылочные исправления не должны менять контракт.
- Бизнес-логику, архитектуру, схему, зависимости и CI не менять ради косметики. Не удалять файлы, пока не подтверждена ненужность; сохранять рабочие unit/DB/native/Android/CI тесты, скрипты и фикстуры.
- Документационные коммиты `[skip ci]`, пропущенные проверки не считать зелёными. Реальные пользовательские данные, почту и платные сервисы использовать только по отдельному разрешению.

## Архитектурные инварианты

- React/TypeScript/Vite, Zustand только для UI, i18next, TanStack Virtual; SQLite — единственный production источник истины. Нет обязательной сети, облака, пользовательского SQL/JS, успешных заглушек или browser/localStorage fallback.
- UI работает через `Repository` и общий TS Core, без своего SQL. Rust/Kotlin — только OS/SQLite-адаптеры. Одно последовательное соединение/точка записи; HLC, индексы, версия и журнал согласованы атомарно. UUID полей стабильны, неизвестные JSON-значения сохраняются.
- До первого публичного релиза — одна dev-схема без цепочки миграций. Несовместимую БД не удалять; после релиза нужны последовательные миграции и recovery. Черновики только создания, не история/БД/sync; очищаются после успешного Save.
- История Top-20 по HLC и стабильному ID; clear/trim, tombstones, Change Log и ACK нельзя ослаблять. Sync только opt-in, независимые SQLite, LWW, replay/ACK, pause/resume/detach, AES-256-GCM, восстановление. Отправлено не означает применено; отклонение по порогу часов запрещено.
- Формулы сохраняются канонически (английские функции, ID), UI локализует; Decimal точный. Секреты исключены из общего FTS/сводок/диагностики; маска/Android system lock не шифруют базу.
- Архив — **незашифрованный** ZIP с проверяемыми данными; активный SQLite не копировать без WAL-контекста. Гант/граф — за границами v4.0.

## Проверки и сопровождение

- Матрица — `.github/workflows/ci.yml`, scope/resume guards — `scripts/ci-scope.mjs` и `tests/unit/ci-scope.test.mjs`. Сохранять unit/DB/native/crash/force-stop сценарии. Browser smoke — стандартный, полный browser UI — расширенная проверка.
- Приоритет ручной проверки: Android → Windows → macOS; Linux application отдельно. GreenMail проверяет изолированный SMTP/IMAP, не реальных провайдеров. Нельзя объявлять физические OEM/SAF/Share/camera, нативный WebView и системные интеграции принятыми по одной сборке.
- Native GTK/Tauri save-picker для archive UI остаётся в test-only карантине; Core/SQLite/Android replacement тесты не удалять. Закреплённый Android debug keystore — публичный тестовый ключ, не release; при смене сертификата сначала проверить внешний backup. SQLite 8.1.1 lifecycle patch перепроверять при обновлении.
- Вместо журнала этапов обновлять факты и границы подтверждения в `implementation.md`; исторические коммиты и CI-run остаются в Git.
