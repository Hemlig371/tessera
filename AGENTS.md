# Tessera — правила Codex

Цель: автономно довести `Hemlig371/tessera` до v4.0 с фактического состояния, не повторяя готовое.

## Источники

- Текущий блок, очередь и точка продолжения — только в [audit.md](audit.md). Каждую сессию читать AGENTS.md и актуальную часть audit.md; остальное адресно: раздел спецификации, код, тесты, [README.md](README.md) (команды), [tests/fixtures/README.md](tests/fixtures/README.md) (наборы).
- Контракт: [target-specification-v4.0.md](target-specification-v4.0.md) (функции), [ui-specification.md](ui-specification.md) (UX). Спецификацию **не изменять**; при расхождении приоритет у «Решений пользователя» ниже.
- Документы внутренние: новых архитектурных не создавать, устаревшие дубли можно удалять. Историю искать в Git, не превращать в задачи. `work/` (игнорируется) читать только по конкретной ссылке или дефекту.

## Git и ход работы

- Только `main`: небольшие осмысленные коммиты, push без согласования. Без веток/PR, переписывания истории, force push, release tags и публичных релизов.
- Перед работой проверить HEAD, дерево и новые удалённые коммиты. Чужие и незавершённые изменения сохранять: без reset/clean поверх WIP, чужой процесс Codex не останавливать.
- Фокус — законченный функционал и корректность логики. Писать только необходимый UI; его полировку и широкую UI-приёмку перенести в конец. Сначала завершить начатый блок, затем по очереди; не останавливаться после плана или каждого коммита.
- Пока блок ждёт нативную приёмку (CI, эмулятор), не простаивать: брать следующую задачу очереди, изолированную от файлов приёмки (§16 спецификации это допускает). Блок принят только после своей приёмки; зависящие от него блоки не начинать.
- Спрашивать только при: необратимом решении или риске потери данных; изменении согласованного поведения/архитектуры; нужде в реальных учётных данных или платных действиях. Остальное разрешено заранее.
- Не добавлять лишние зависимости, слои и рефакторинг; размер файла не дефект. Модель и правила не менять ради UI. В конце сессии оставить в audit.md краткую точку продолжения.

## Инварианты

- React/TypeScript/Vite; Zustand только для UI; TanStack Virtual; i18next (русский по умолчанию). SQLite — единственный источник истины; production localStorage/sql.js/browser fallback и успешные заглушки запрещены.
- Бизнес-правила, DDL/bootstrap, HLC, LWW, история и Change Log — в общем TS-ядре; Rust/Kotlin — только OS/SQLite-адаптеры. UI идёт через Repository/ядро, без своего SQL.
- Одно последовательное соединение и одна точка записи. Запись, HLC, производные индексы, требуемая версия и событие журнала — атомарно. UUID полей стабильны; неизвестные JSON-значения сохраняются.
- До публичного релиза — одна dev-схема без цепочки миграций. Несовместимую БД не удалять и не перезаписывать: сохранить данные, объяснить совместимый экспорт. После релиза — версионированные миграции, согласованные snapshots, проверка восстановления; слепой downgrade запрещён.
- Явное Save создаёт пользовательскую версию; Share и быстрые действия — по их контрактам. Черновик — только создания, один на коллекцию, восстановленный ввод приоритетен; это не запись БД, не история и не sync. Удалять только после успешного Save.
- История — Top-20 по `(HLC, стабильный ID версии)`, без срока возраста; позднее старое не вытесняет новое. Маркеры clear/trim не дают старым пакетам вернуть очищенное.
- Change Log отделён от истории и ограничен без sync. Первое включение строит baseline из актуальных таблиц; active/paused сохраняют нужные события; detached получает новый `dataset_id`. Компактация восстанавливается после сбоя, а не заменяется безусловным DELETE.
- «Экспорт/Импорт БД» — единственная пользовательская backup/restore-функция. Технические snapshots и recovery-копии допустимы; активный `.sqlite` без WAL-контекста не копировать.
- Local-first: нет обязательных сети, сервера, аккаунта, постоянного сервиса, пользовательского JS/SQL и облачной телеметрии. Секреты не индексировать и не логировать. Фундамент merge/HLC не объявлять готовым sync.

## Проверки и CI

- Перед функциональным коммитом локально: typecheck, lint, релевантные unit/DB. Markdown-only: проверить diff и ссылки, без браузера, сборки и CI.
- Нативный код (Kotlin/Java/Rust, Gradle) компилировать локально до CI; SDK/JDK/Gradle ставить в `work/`. Ошибки компиляции не должны тратить CI-прогон.
- Промежуточные коммиты — `[skip ci]`; ≤6–8 коммитов на блок. Полный CI — раз в конце блока, максимум один повтор; зелёное неизменённое не повторять и не ослаблять. Draft CI-профиль не считать утверждённым правилом или проверенным результатом.
- В приоритетном CI оставлять один необходимый UI-smoke (`test:e2e:smoke`); полный `test:e2e` сохранить для итоговой UI-приёмки. Unit/DB и native-проверки рисков данных не сокращать ради UI-скорости.
- Пропущенные jobs не зелёные; разные прогоны не выдавать за один полный зелёный HEAD.
- Красный тест сначала классифицировать. Дефект ядра/данных и реальный дефект приложения — **без карантина**: чинить код или тест.
- Test-only проблемы UI/native (селектор, тайминг, фокус, подпись, раскладка): после второй неудачной правки того же теста — `fixme`/`@quarantine` с причиной, запись в «Известные проблемы» audit.md (имя, симптом, попытки), исключение из обязательного CI. До конца блока не возвращаться; максимум две красные итерации CI на UI. Карантин не блокирует завершённый функциональный блок; перед M7 исправить или удалить с ведома владельца.

## Тесты

- Ядро: тест на правило. UI-тесты сократить до необходимого минимума; широкую UI-приёмку и полировку выполнять в конце, не задерживать функциональные блоки ради UI-сценариев. Native/kill-тесты — только для рисков данных (сохранение, архив, вложения, sync), не ради косметики (Back/Escape/клавиатура).
- Только необходимые новые UI-тесты: роли и `data-testid`, ожидание состояния/запроса без пауз. Не выполнять повторные UI-проходы ради формального счётчика; нестабильный тест не включать в обязательную приёмку. Тесты не удалять без записанной причины.
- Приоритет платформ: Android → Windows → macOS. Linux не приоритетен; его проверки/сборки можно пропускать там, где они замедляют разработку, честно отмечая область доказательств. Linux-host для Android CI этим не запрещён.
- Браузер — только для необходимой проверки существенного функционала или конкретного дефекта; сначала код, trace и логи. Полировка и широкая UI-приёмка — в конце; функциональный E2E не доказывает визуальную готовность. Критерии пакетной UX-приёмки (390 px/150%, 1280 px, темы, состояния) — в [ui-specification.md](ui-specification.md).

## Очередь, отчёты, версии

- Очередь M1–M7 (архив → типы/формулы → режимы/сводки → интеграции → sync → шифрование/почта → сквозная приёмка) и её статус — только в audit.md.
- После M1 и M2: отчёт ≤15 строк (готовое, проверки, шаги телефона, красные/карантинные тесты, APK), затем следующий блок без ожидания ответа. Регулярные обновления — кратко.
- Версия — один раз на значимый блок: minor 0.x, самостоятельные исправления — при необходимости patch. npm/Cargo/Tauri/Android и lock-файлы согласованы, versionCode растёт. Версия приложения ≠ v4.0 и не означает релиз.

## Решения пользователя 17.11.2026 — не пересматривать без запроса

- Sync необязателен/выключен. Сначала независимые SQLite и файловый протокол (повторы/перестановки/пропуски/offline/LWW/идемпотентность/история/tombstones/ACK/pause-resume-detach/recovery), потом криптография и нативный SMTP/IMAP как перенос непрозрачных байтов. Письма приложение не удаляет; «отправлено» ≠ «применено»; реальный ящик проверяет пользователь.
- Расхождение часов принято: не предупреждать, не отклонять пакеты по порогу. Формульные результаты не синхронизировать.
- Формулы сохраняются канонически: английские функции, ID полей/связей. UI локализован (`СУММ(...; ...)` / `SUM(...,...)`); смена локали не меняет сохранённую формулу.
- Архив — незашифрованный ZIP, manifest.json + открытые JSON/NDJSON + малые оригиналы/хеши; крупные — метаданные/заглушки. Предупреждать «архив не зашифрован». Парольной защиты в v4.0 нет.
- M3/v4.0 — Kanban, календарь, дерево, сводки. Гант/граф после первого релиза, в v4.0 не делать.
- Блокировка только Android: стандартная системная авторизация/биометрия, без своего PIN; desktop-блокировки нет. UI-блокировка не шифрует SQLite.
- Штрихкод/QR — текст с подписью, без сканирования. Камера для QR-ключа группы — отдельный M6. «Секрет» — маскирование без шифрования SQLite/открытого ZIP; исключить из FTS, общих списков/сводок, шаблонов и диагностики.
