# Tessera — правила Codex

## Цель и источники

- Автономно довести `Hemlig371/tessera` до v4.0 с фактического состояния, без повторной реализации готового. Текущий блок, очередь и точка продолжения — только в [audit.md](audit.md).
- Функциональный контракт — [target-specification-v4.0.md](target-specification-v4.0.md); UX — [ui-specification.md](ui-specification.md). Основную спецификацию **не изменять**. Уточнения пользователя ниже имеют приоритет при расхождении.
- Всегда читать AGENTS.md и текущую часть audit.md. Остальное — адресно: нужный раздел спецификации, код и тесты; [README.md](README.md) для команд, [tests/fixtures/README.md](tests/fixtures/README.md) для универсальных наборов.
- Документы внутренние. Не создавать новые архитектурные документы; удалять устаревшие дубли разрешено. Исторические подробности искать в Git, не превращать их в открытые задачи. Игнорируемый `work/` читать только по конкретной ссылке/дефекту.

## Работа и Git

- Только `main`: небольшие осмысленные коммиты и push без согласования. Без веток/PR, переписывания истории, force push, release tags и публичных релизов.
- Перед работой проверить HEAD, рабочее дерево и новые удалённые коммиты; сохранить незавершённые/чужие изменения. Не выполнять reset/clean поверх WIP и не останавливать другой процесс Codex.
- Фокус — законченные блоки функционала **вместе с UI**, приёмка пакетная. Сначала завершить начатый блок, затем идти по очереди; не останавливаться после плана или каждого коммита.
- Спрашивать только при необратимом решении/неустранимом риске потери данных, необходимости изменить согласованное поведение/архитектуру или получить реальные учётные данные/платные действия. Обычные исправления, проверки и переходы заранее разрешены.
- Не добавлять ненужные зависимости, слои и рефакторинг; размер файла сам по себе не дефект. Не менять модель/правила ради UI. При завершении сессии оставить краткую точку продолжения в audit.md.

## Инварианты

- React/TypeScript/Vite; Zustand только UI, TanStack Virtual, i18next (русский по умолчанию). SQLite — единственный источник истины; production localStorage/sql.js/browser fallback и успешные заглушки запрещены.
- Бизнес-правила, DDL/bootstrap, HLC, LWW, история и Change Log — общее TS-ядро; Rust/Kotlin — OS/SQLite-адаптеры. UI использует Repository/общий Core, не собственный SQL.
- Одно последовательное соединение/точка записи. Изменение записи, HLC, производных индексов, требуемой версии и события журнала атомарно. UUID полей стабильны; неизвестные JSON-значения сохраняются.
- До публичного релиза — одна текущая dev-схема без цепочки миграций. Несовместимую БД не удалять/перезаписывать; сохранить данные и объяснить совместимый экспорт. После релиза — версионированные миграции, согласованные snapshots и проверка восстановления; слепой downgrade запрещён.
- Явное Save создаёт пользовательскую версию; предусмотренные Share/быстрые действия реализовать по их контрактам. Черновик только создания, один на коллекцию, восстановленный ввод приоритетен; не запись БД/история/sync. Удалять только после успешного Save.
- История — Top-20 по `(HLC, стабильный ID версии)`, без срока возраста; позднее старое не вытесняет новое. Clear/trim markers не дают старым пакетам вернуть очищенное.
- Change Log отделён от истории: ограничен без sync; первое включение строит baseline из актуальных таблиц, active/paused сохраняют необходимые события, detached получает новый dataset_id. Компактация восстанавливается после сбоя, не подменяется безусловным DELETE.
- «Экспорт/Импорт БД» — единственная пользовательская backup/restore-функция. Технические snapshots и recovery-копии допустимы; активный `.sqlite` без WAL-контекста не копировать.
- Local-first: нет обязательных сети/сервера/аккаунта/постоянного сервиса, произвольного пользовательского JS/SQL и облачной телеметрии. Секреты не индексировать и не логировать; фундамент merge/HLC не объявлять готовым sync.

## Порядок и приёмка

- M1 перенос/архив → M2 типы/Decimal/формулы → M3 режимы/сводки → M4 недостающие системные интеграции → M5 локальный sync → M6 шифрование/почта → M7 сквозная приёмка. Детали/статус не дублировать здесь, они в audit.md.
- ≤6–8 коммитов на блок; промежуточные `[skip ci]`. Перед функциональным коммитом локально typecheck, lint, релевантные unit/DB. Markdown-only: diff/ссылки, без браузера/сборки/CI.
- Полный CI один раз в конце блока + максимум один повтор. Не повторять зелёные неизменённые проверки без причины и не ослаблять существующие. Draft CI-профиль не считать утверждённым правилом или проверенным результатом.
- Ядро: тест на правило. UI: один главный сценарий на блок. Native/kill — только риски данных (сохранение, архив, вложения, sync); не добавлять native Back/Escape/клавиатуру ради косметики.
- Браузер — приёмка существенного блока либо конкретный дефект, не после каждой правки. Сначала код/имеющиеся trace/логи. UI-полировка только затронутых экранов; функциональный E2E не доказывает визуальную готовность. При пакетной UX-приёмке: телефон ~390 px/150%, desktop ~1280 px, обе темы, длинные данные, loading/empty/error, фокус и переполнение.
- До исправления красного теста классифицировать падение: ядро/данные **и реальный дефект приложения — без карантина**, исправлять код/тест.
- Для test-only UI/native проблемы (селектор, тайминг, фокус, подпись, раскладка): после второй неудачной правки **того же теста** — fixme/@quarantine с причиной, запись в «Известные проблемы» audit.md (имя/симптом/попытки), исключение из обязательного CI. До конца блока не возвращаться; бюджет красных UI — максимум две итерации CI. Карантинные UI не блокируют завершённый функциональный блок.
- Новые UI-тесты: роли/data-testid, без позиционных и текстовых селекторов; ожидание состояния/запроса вместо пауз; три последовательных локальных прохода до коммита. Нестабильный новый тест не коммитить; тесты не удалять без записанной причины. Перед M7 карантин исправить либо удалить с ведома пользователя.
- После M1/M2: отчёт ≤15 строк (готовое, проверки, конкретные шаги телефона, красные/карантинные тесты, APK), затем следующий блок без ожидания ответа. Пропущенные jobs не зелёные, разные прогоны не представлять одним полным зелёным HEAD. Регулярные обновления — кратко.
- Версия один раз на значимый блок: minor 0.x, самостоятельные исправления при необходимости patch; npm/Cargo/Tauri/Android и lock-файлы согласованы, versionCode растёт. Версия приложения ≠ v4.0 и не означает релиз.

## Решения пользователя 17.11.2026 — не пересматривать без запроса

- Sync необязателен/выключен. Сначала независимые SQLite и файловый протокол (повторы/перестановки/пропуски/offline/LWW/идемпотентность/история/tombstones/ACK/pause-resume-detach/recovery), потом криптография и нативный SMTP/IMAP как перенос непрозрачных байтов. Письма приложение не удаляет; «отправлено» ≠ «применено»; реальный ящик проверяет пользователь.
- Расхождение часов принято: не предупреждать, не отклонять пакеты по порогу. Формульные результаты не синхронизировать.
- Формулы сохраняются канонически: английские функции, ID полей/связей. UI локализован (`СУММ(...; ...)` / `SUM(...,...)`); смена локали не меняет сохранённую формулу.
- Архив — незашифрованный ZIP, manifest.json + открытые JSON/NDJSON + малые оригиналы/хеши; крупные — метаданные/заглушки. Предупреждать «архив не зашифрован». Парольной защиты в v4.0 нет.
- M3/v4.0 — Kanban, календарь, дерево, сводки. Гант/граф после первого релиза, в v4.0 не делать.
- Блокировка только Android: стандартная системная авторизация/биометрия, без своего PIN; desktop-блокировки нет. UI-блокировка не шифрует SQLite.
- Штрихкод/QR — текст с подписью, без сканирования. Камера для QR-ключа группы — отдельный M6. «Секрет» — маскирование без шифрования SQLite/открытого ZIP; исключить из FTS, общих списков/сводок, шаблонов и диагностики.
