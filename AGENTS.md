# Tessera

- По указанию пользователя работать непосредственно в `main`, без PR. Сохранять этапы отдельными проверяемыми коммитами; публикацию релиза и необратимые действия выполнять только в согласованном объёме.
- Главный функциональный контракт — `target-specification-v4.0.md`; согласованный целевой UI/UX — [`ui-specification.md`](ui-specification.md); реальные пользовательские тестовые сценарии (только dev/CI) — [`tests/fixtures/README.md`](tests/fixtures/README.md). Перед началом каждого этапа обязательно прочитать [`audit.md`](audit.md): подтверждённые замечания, согласованные решения, приоритеты и критерии тестирования. Проверять актуальность замечаний на текущем `main`, устранять относящиеся к этапу риски и честно отмечать незакрытые. Если аудит и спецификация расходятся, не подменять требования молча — зафиксировать противоречие и предложить минимальное согласование. Прототип — только пример идей; совместимость с его кодом и данными не требуется. **До первого публичного релиза** не поддерживать обновление между промежуточными dev-схемами: использовать одну актуальную схему/bootstrap для чистой установки, не сохранять цепочку dev-миграций ради совместимости. Несовместимую dev-базу нельзя удалять молча: предупредить пользователя и предложить заранее экспортировать данные. **После первого публичного релиза** обновлять пользовательские базы последовательными версионированными миграциями с проверкой сохранности данных и резервной копией перед рискованными изменениями. Не менять функциональные требования ради скорости.
- Работать небольшими проверяемыми этапами. Пользователь разрешил последовательную реализацию всей v4.0 небольшими проверяемыми этапами без повторного согласования каждого этапа. **Исходное состояние при пересмотре UX — v0.5.0, базовая структура/входящие/связи/быстрые формы уже реализованы и миграции 1–5 выпущены; это не новая разработка с нуля.** В продолжении реализованы черновики **только создания** (0.6.0), именованные профили существующих режимов (0.7.0) и пресеты (0.8.0), с отдельными коммитами и проверкой CI. Добавлены Markdown/перенос из входящих (0.9.0). A-04 реализован отдельным этапом (0.10.0): прогресс/отмена CSV и атомарное восстановление. Настройки оформления устройства (0.11.0) внедрены отдельно от будущего редизайна. Отдельный режим конструктора (0.12.0) скрывает настройки схемы в обычной работе, сохраняя текущие редакторы и предпросмотр. Строки 1–3 колонки, группы и свёрнутые поля формы/карточки/быстрой формы (0.13.0) добавлены без переписывания старых настроек при открытии. Основные редакторы и карточка перенесены на отдельные экраны (0.14.0), со старым механизмом Save/черновиков; простая отмена/возврат сохраняют контекст. Главные каталоги/старты библиотек, возврат позиции после Save/глобального поиска и локальная история реализованы следующими блоками; далее — оставшиеся риски аудита, Android Share и функции v4.0, адаптивный UX и тестовые библиотеки; не считать весь целевой UX, формулы, расширенные режимы или синхронизацию уже готовыми. Статус готовности каждого коммита подтверждать CI, не объявлять незавершённый прогон успешным. Share файлов, вложения, Decimal/формулы, режимы/сводки, история и почта проверяются отдельными этапами. Ручная приёмка дополняет автотесты там, где нужны физические устройства/реальные личные учётные данные/подписи.
- React/TypeScript/Vite, Zustand только для UI, TanStack Virtual и ограниченные SQL-выборки. Строки UI — через i18next, русский по умолчанию.
- Бизнес-правила, DDL, миграции, HLC, история и журнал — в общем TypeScript-ядре. Rust/Kotlin — только адаптеры ОС/SQLite. UI обращается к repository API, не к SQL.
- Нативная SQLite — единственный источник истины. Запрещены production localStorage, sql.js, browser fallback и скрытые заглушки. Android сначала использует бесплатный community SQLite.
- Все обращения к соединению проходят через последовательную очередь адаптера. Правка объекта, версия и change_log атомарны; HLC сохраняется в той же транзакции. Desktop — один процесс-писатель.
- UUID полей стабильны; записи в одной таблице records с валидным JSON-объектом. Неизвестные значения сохранять. До первого публичного релиза актуальная схема создаётся единым транзакционным bootstrap без upgrade-цепочки между dev-этапами. После релиза новая версия схемы — последовательная транзакционная миграция; перед рискованным изменением существующей пользовательской БД — согласованный backup. Не сбрасывать неподдерживаемую БД.
- Только явное сохранение формы создаёт запись/пользовательскую версию (Android Share — осознанное прямое создание во «Входящих» без формы). «Отмена» редактирования существующей записи ничего не пишет. «Закрыть» создание сохраняет **один локальный черновик на коллекцию**, восстановление происходит при следующем создании, **удаление только после успешного сохранения**; редактирование существующей записи не участвует в системе черновиков. Повреждённый файл сначала сохранять байт-в-байт в проверенную приватную recovery-копию и только затем освобождать рабочий путь для нового создания; валидные черновики этим механизмом не удалять. Черновик — локальный файл без секретов, записей, версий, журнала и синхронизации. Быстрые действия без пользовательской версии.
- Никакого произвольного JS/SQL пользователя, фонового сервиса, обязательного аккаунта или сети. Секреты не логировать и не индексировать.
- Существенные изменения проверять реальными тестами; тесты/бенчмарки только dev/CI. Не выдавать Node SQLite за проверенный Capacitor/Tauri bridge. Не реализованный sync-протокол не считать протестированным.
- По последнему указанию пользователя экономить проверки: для небольших изменений запускать только относящиеся к ним целевые тесты/проверки. Полные `typecheck`, `lint`, `test:all` и `build` — после значительного связанного блока работы, а не каждого действия или малого этапа. Новые миграции всегда проверять на сохранность существующей БД; критические изменения транзакций/синхронизации проверять соответствующими DB/native-контрактами. Небольшие коммиты сохранять в `main`, публикации группировать по завершённым блокам. Обычный CI выполняет быстрые проверки; тяжёлая native-матрица запускается автоматически для native/build/schema-контрактов, для tags и по `[full ci]` / `[native ci]`. После значимого межплатформенного этапа или перед контрольной точкой обязателен полный запуск: `gh workflow run ci.yml --ref main -f full_native=true`; ручной запуск по умолчанию полный. Для изолированного повтора Android при уже проверенных неизменённых исходниках остальных платформ доступен ручной `native_target=android`; полный профиль `all` остаётся значением по умолчанию. Не считать пропущенные native jobs успешной приёмкой платформ. Проверять CI опубликованного блока и честно указывать блокировки. Windows/Android-проверки требуют соответствующей среды.
- Не добавлять необязательные зависимости или дополнительные архитектурные документы. Отдельный `ui-specification.md` и описание тестовых библиотек **созданы по явному решению пользователя**, их нужно учитывать. Технический контракт — код, миграции, тесты; команды и ограничения — README. До первого публичного релиза свести текущую цепочку dev-миграций к единому bootstrap актуальной схемы; совместимость промежуточных dev-баз не требуется, но нельзя молча уничтожать их данные. После релиза новые изменения схемы вводить последовательными миграциями с безопасным upgrade, резервной копией и тестами сохранности/восстановления пользовательских данных. Не вшивать тестовые библиотеки в пользовательский бинарник.
- Дизайн-система и навигация внедряются инкрементально; не удалять текущие рабочие функции ради мгновенного редизайна. Профили отображения — новая сохранённая конфигурация **одной коллекции**, не ранее исключённая концепция «Представления». Пресеты создания не являются записями. Любые конфликты спецификации, UX и аудита фиксировать и устранять без молчаливого изменения продукта.
