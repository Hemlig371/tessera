# Tessera

- По указанию пользователя работать непосредственно в `main`, без PR. Сохранять этапы отдельными проверяемыми коммитами; публикацию релиза и необратимые действия выполнять только в согласованном объёме.
- Главный функциональный контракт — `target-specification-v4.0.md`; согласованный целевой UI/UX — [`ui-specification.md`](ui-specification.md); реальные пользовательские тестовые сценарии (только dev/CI) — [`tests/fixtures/README.md`](tests/fixtures/README.md). Перед началом каждого этапа обязательно прочитать [`audit.md`](audit.md): подтверждённые замечания, согласованные решения, приоритеты и критерии тестирования. Проверять актуальность замечаний на текущем `main`, устранять относящиеся к этапу риски и честно отмечать незакрытые. Если аудит и спецификация расходятся, не подменять требования молча — зафиксировать противоречие и предложить минимальное согласование. Прототип — только пример идей; совместимость с его кодом и данными не требуется. Базы выпущенных версий Tessera сохранять миграциями. Не менять функциональные требования ради скорости.
- Работать небольшими проверяемыми этапами. Пользователь разрешил последовательную реализацию всей v4.0 небольшими проверяемыми этапами без повторного согласования каждого этапа. **Исходное состояние при пересмотре UX — v0.5.0, базовая структура/входящие/связи/быстрые формы уже реализованы и миграции 1–5 выпущены; это не новая разработка с нуля.** В продолжении реализованы черновики **только создания** (0.6.0), именованные профили существующих режимов (0.7.0) и пресеты (0.8.0), с отдельными коммитами и проверкой CI. Добавлены Markdown/перенос из входящих (0.9.0). A-04 реализован отдельным этапом (0.10.0): прогресс/отмена CSV и атомарное восстановление. Далее — Android Share, оставшиеся риски аудита и функции v4.0, адаптивный UX и тестовые библиотеки; не считать весь целевой UX, формулы, расширенные режимы или синхронизацию уже готовыми. Статус готовности каждого коммита подтверждать CI, не объявлять незавершённый прогон успешным. Share файлов, вложения, Decimal/формулы, режимы/сводки, история и почта проверяются отдельными этапами. Ручная приёмка дополняет автотесты там, где нужны физические устройства/реальные личные учётные данные/подписи.
- React/TypeScript/Vite, Zustand только для UI, TanStack Virtual и ограниченные SQL-выборки. Строки UI — через i18next, русский по умолчанию.
- Бизнес-правила, DDL, миграции, HLC, история и журнал — в общем TypeScript-ядре. Rust/Kotlin — только адаптеры ОС/SQLite. UI обращается к repository API, не к SQL.
- Нативная SQLite — единственный источник истины. Запрещены production localStorage, sql.js, browser fallback и скрытые заглушки. Android сначала использует бесплатный community SQLite.
- Все обращения к соединению проходят через последовательную очередь адаптера. Правка объекта, версия и change_log атомарны; HLC сохраняется в той же транзакции. Desktop — один процесс-писатель.
- UUID полей стабильны; записи в одной таблице records с валидным JSON-объектом. Неизвестные значения сохранять. Новая схема — новая транзакционная миграция; перед изменением существующей схемы согласованный backup. Не сбрасывать неподдерживаемую БД.
- Только явное сохранение формы создаёт запись/пользовательскую версию (Android Share — осознанное прямое создание во «Входящих» без формы). «Отмена» редактирования существующей записи ничего не пишет. «Закрыть» создание сохраняет **один локальный черновик на коллекцию**, восстановление происходит при следующем создании, **удаление только после успешного сохранения**; редактирование существующей записи не участвует в системе черновиков. Черновик — локальный файл без секретов, записей, версий, журнала и синхронизации. Быстрые действия без пользовательской версии.
- Никакого произвольного JS/SQL пользователя, фонового сервиса, обязательного аккаунта или сети. Секреты не логировать и не индексировать.
- Существенные изменения проверять реальными тестами; тесты/бенчмарки только dev/CI. Не выдавать Node SQLite за проверенный Capacitor/Tauri bridge. Не реализованный sync-протокол не считать протестированным.
- Перед завершением: `npm run typecheck`, `npm run lint`, `npm run test:all`, `npm run build`; при доступном Rust — `npm run test:native`. Проверить CI и честно указать блокировки. Windows/Android-проверки требуют соответствующей среды.
- Не добавлять необязательные зависимости или дополнительные архитектурные документы. Отдельный `ui-specification.md` и описание тестовых библиотек **созданы по явному решению пользователя**, их нужно учитывать. Технический контракт — код, миграции, тесты; команды и ограничения — README. Существующие миграции 1–5 не переписывать; новые модели/поля вводить новыми миграциями с безопасным upgrade и проверкой сохранности настроек 0.5.0. Не вшивать тестовые библиотеки в пользовательский бинарник.
- Дизайн-система и навигация внедряются инкрементально; не удалять текущие рабочие функции ради мгновенного редизайна. Профили отображения — новая сохранённая конфигурация **одной коллекции**, не ранее исключённая концепция «Представления». Пресеты создания не являются записями. Любые конфликты спецификации, UX и аудита фиксировать и устранять без молчаливого изменения продукта.
