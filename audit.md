### M1 — в работе

Новая привязка вложения допускается только через объявленные file/image поля. UUID в строке/неизвестном JSON сохраняется как данные, но не публикует staged-файл и не создаёт metadata/location/event. Ранее связанные файлы после переноса и их история сохраняются. CSP Tauri разрешает `img-src blob:`; реальный WebView-предпросмотр ещё предстоит проверить в конце M1. Typecheck/lint и 17 целевых DB/unit-тестов прошли; native/UI пока не запускались.

Промежуточная реализация M1: открытый ZIP STORE/ZIP64, `manifest.json`, доменные NDJSON-сущности (без DDL/производных SQLite), SHA-256 частей/вложений и ZIP CRC; согласованное чтение в одной WAL-транзакции. Новый device_id, независимый dataset по выбору, отсутствие transport/local_settings/секретов ОС; версии/clear markers/tombstones сохраняются. Малые оригиналы, крупные и отсутствующие — явные заглушки. Локально Node+Rust: 65 целевых тестов архива/файлов/ZIP; Rust abrupt-death на каждом rename (20 точек), повторное восстановление проверено. Главный UI-сценарий прошёл 3 раза до мобильного уточнения; native-платформы/системные диалоги/итоговый CI ещё не приняты. M1 остаётся в работе.

## Актуальный статус и порядок работ — 16.11.2026

### Что действительно реализовано

- Общее TypeScript-ядро, Repository API, нативная SQLite через Tauri/Rust и Capacitor/Kotlin, последовательная очередь, единый bootstrap, поиск/FTS, индексы и SQL-пагинация.
- Базовая модель библиотек, коллекций, полей, записей, прямых/обратных связей, «Входящих», CSV и быстрых форм.
- Локальные черновики только создания, пресеты, именованные профили существующих режимов, Markdown и перенос из «Входящих».
- Главные каталоги, старты библиотек, навигация/возврат, Android-ярлыки (с ручным подтверждением системного диалога).
- История Top-20, восстановление версий, общая корзина, сроки хранения и терминальные tombstones.
- HLC, Change Log, baseline, active/paused/detached и локальные merge-примитивы. Это **фундамент**, а не законченный обмен между устройствами.

### Завершённый локальный блок вложений — 0.17.0 / стабилизация 0.17.1

Начатый до обновления очереди блок завершён по прямому поручению пользователя. Поля file/image (одно/много), приватные оригиналы под техническими UUID, SHA-256/имя/MIME/размер/владелец в SQLite. Порции 256 КиБ, staging до явного Save без записи/версии/HLC/журнала; Save атомарно связывает метаданные, историю, местонахождение, журнал и индексы. Черновик создания сохраняет готовые ссылки; отмена редактирования очищает неопубликованные копии. Перенос из «Входящих» сохраняет ID/историю/файлы; ссылки из прежней схемы доступны в карточке и истории.

Отсоединение из поля сохраняет исторические байты. Удаление единственной известной локальной копии требует предупреждения; возврат проверяет точный размер/хеш и не создаёт пользовательскую версию. Метаданные purge очищаются атомарно; долговечный GC возобновляется после сбоя, неисправная порция не блокирует остальные файлы. Маркер незавершённого возврата переживает первый GC: даже после process-death поздно опубликованные/частичные байты окончательно удалённой записи очищаются при запуске. Android-монитор IO общий для экземпляров при пересоздании Activity. Экспортное имя ограничено UTF-8-байтами, сохраняет расширение/целые Unicode-символы.

UI: формы/«Входящие»/карточка/история, индивидуальный экспорт, проверка наличия/хеша, понятные состояния missing/corrupt, безопасный просмотр малых растров. Общий порог 10 МиБ настраивается и входит в будущий baseline. **Полный протокол передачи байтов не реализован.** Крупные файлы/групповой экспорт, кэш миниатюр и архив остаются в очереди §8/§10.

**Схема:** `tessera-dev-bootstrap-2`, один актуальный дорелизный bootstrap. Базы 0.16.0 и промежуточные dev-схемы отклоняются без удаления/перезаписи. Сохранять исходный каталог и использовать совместимую сборку; полного переносимого архива пока нет.

### Правило приёмки UI

UI имеет две независимые оси: функциональное поведение и визуальное качество. Текущие Playwright/Android сценарии в основном проверяют первую. Реализация идёт законченными блоками UI/функций; общий осмотр на целевых размерах, темах и увеличении текста выполняется при пакетной приёмке блока. Существующие тесты сохраняются; промежуточные CSS-правки не требуют каждого отдельного запуска браузера или пользовательского сценария.

### Экономная стратегия проверок

- Markdown-only: diff/ссылки, без CI.
- Между небольшими связанными изменениями: diff и необходимые дешёвые статические проверки; не запускать браузер/сборку/сценарии на каждый коммит.
- UI/CSS/React/навигация: сначала законченный блок, затем общая сборка/типизация, соответствующие сценарии и визуальный осмотр.
- Repository/SQLite/формулы: сначала связанный функциональный блок, затем его unit/DB-контракты; транзакции, bootstrap и восстановление включают rollback/reopen.
- Rust/Kotlin/Capacitor/Tauri: соответствующие native-контракты после законченного блока.
- Новый подтверждённый дефект: сначала имеющиеся trace/логи/код; отдельное воспроизведение только по необходимости. Успешные проверки неизменённого кода учитывать повторно.
- Полная native-матрица — после значимого межплатформенного этапа и перед контрольной точкой; пропущенные jobs не считаются успешными.


## 1. Итог и уже подтверждённое

Стек и основная архитектура соответствуют целевой модели: React/TypeScript/Vite, общая бизнес-логика на TypeScript, Capacitor Android с `@capacitor-community/sqlite`, Tauri 2/Rust с `rusqlite`, настоящая SQLite как источник истины, JSON-значения в `records`, FTS5, локальные индексы, SQL-пагинация и виртуализация. Аварийные сценарии проверяют удаление/восстановление/purge с откатом данных, истории, HLC и журнала. Это один зелёный полный прогон текущего кода, в отличие от исторической составной приёмки 0.15.0.

**Тестовый lifecycle:** новый foreground-потребитель выявил, что E2E FileAdapter отправлял active при pagehide, если document ещё visible; это запускало транзакцию во время reload тестовой страницы. Test adapter приведён к production-контракту: pagehide всегда inactive. Производственный адаптер уже выполнял это правило. Повторный reload корзины проходит.

## 2. Текущие замечания к коду

### A-01 · P1 · Проверка устаревшей формы перед явным сохранением

**Изменение 0.6.0:** добавлены обязательный исходный HLC для обычного редактирования и явный выбор загрузки текущего состояния/сохранения своей редакции. DB-тест проверяет отсутствие изменений records/versions/HLC/journal/FTS при отказе; UI-сценарий проверяет подтверждённую редакцию. Нативная матрица A-01/F-06 и A-02 прошла на `eb4637f`: https://github.com/Hemlig371/tessera/actions/runs/43718025682.

**Причина в 0.5.0 (исправлено):** обычное сохранение не проверяло исходный HLC открытой формы. Теперь проверка обязательна и при повторном подтверждении своей редакции.

**Действующий контракт:** передавать исходный HLC из открытой формы в обычное сохранение; если текущий HLC изменился, **не выполнять молчаливую перезапись**. UI должен дать осознанный выбор, соответствующий требованиям явного сохранения. Это локальная защита формы, **не** механизм field-level merge и не изменение правила LWW для конкурирующих удалённых редакций.

**Приёмка:** тесты «старая форма / свежая запись», отсутствие новой версии и записи `change_log` при отклонённом сохранении, сохранение новой редакции при подтверждённом действии.

### A-02 · P2 · Изоляция состояния перестройки индексов

**Изменение после 0.6.0:** проверка FTS/текстовых ключей ограничена областью запроса и применяется только при использовании этих кэшей. Проверки relation/backlink ограничены их исходными коллекциями (для прямой страницы — нужными записями). Регрессионные DB-тесты воспроизводят оба дефекта на старом коде и проверяют поиск/сортировку, числовые запросы, страницы/превью/фильтры связей и CSV.

**Причина в 0.5.0 (исправлено):** проверка готовности производных ключей затрагивала независимые коллекции. Сейчас она ограничена областью и нужными ключами конкретного запроса.

**Действующий контракт:** ограничить проверку областью и необходимыми ключами **конкретного** запроса. Не допускать ложной блокировки независимых коллекций; сохранять отказ от выдачи частично индексированных результатов там, где индекс действительно необходим.

**Приёмка:** тест с двумя коллекциями: у A перестройка, у B сортировка/поиск работают; A корректно сигнализирует о временной неготовности нужного индекса.

### A-03 · P1 до включения синхронизации · Рост `change_log` и повторение полного payload

**Наблюдение:** `src/core/repository.ts`, `persistEntry()`: состояние записи хранится в `records`, снимок — в `record_versions`, и ещё два события с содержимым попадают в `change_log` (`record` и `record_version`). В 0.5.0 политика очистки отсутствовала. На текущем main автономные записи не пополняют журнал, а active/paused и безопасная компактация реализованы в ядре (D-02). Почтового транспорта ещё нет.

**Согласованная политика:**
- Синхронизация **необязательна и выключена по умолчанию**. В самостоятельной базе пользовательские версии создаются, но передаваемый журнал не должен бесконечно накапливаться. Допустимо не писать `change_log` до первого подключения; альтернативная техническая реализация разрешена, если доказано, что размер ограничен и данные не теряются.
- Различать `never_configured`, `active`, `paused`, `detached` (названия внутренние). `paused` **не означает** сброс очереди или истории; при повторном включении накопленные изменения должны сохраниться. `detached` — отдельная независимая база/идентичность.
- При первом включении обмена исходное состояние формируется **из актуальных таблиц**; локальный «Экспорт БД» и почтовый транспорт не смешивать.
- После подключения определить границы хранения, возобновление после сбоев и безопасную компактацию; не удалять данные, которые ещё понадобятся принимающим устройствам.
- Метаданные/ссылки вместо полного содержимого в журнале допустимы **только** если протокол гарантирует доступность конкретных исторических версий, нужных для отправки; нельзя незаметно заменить историческое событие текущим состоянием.
- История версий, `change_log`, исходные записи и резервные копии — разные сущности с разным жизненным циклом.

**Приёмка:** независимая база делает сотни/тысячи сохранений без линейного роста избыточного транспортного журнала; `paused` не теряет дельты; повторный запуск не дублирует события; первоначальное включение синхронизации не требует архива.

### A-04 · P2 · Большие CSV-импорты и отзывчивость

**Изменение 0.10.0:** добавлены прогресс и кооперативная отмена чтения/разбора/предпросмотра/импорта. Одна транзакция сохраняется до финального commit; UI явно показывает фазу фиксации. DB-контракты проверяют полный откат поздней ошибки и отмены (включая HLC, версии, журнал, FTS/связи), отдельный Rust-процесс принудительно завершается внутри импорта с проверкой восстановления на диске. Playwright проверяет доступность отмены и успешный повторный импорт; native acceptance включает Capacitor API и Tauri UI. Native acceptance CSV, Markdown и оформления прошла на Android/Windows/macOS/Linux в `55aba86`: https://github.com/Hemlig371/tessera/actions/runs/43744964144 (8/8 jobs). Локального Android/GTK нет. Чтение порционное, но разобранный CSV пока в памяти (лимит файла 100 МиБ); автоматическое продолжение после перезапуска относится к F-05 и не реализовано.

**Наблюдение:** `importEntries()` делает атомарную транзакцию с порционными SQL-командами. Это надёжно по данным, но единственное соединение занято на время транзакции.

**Действующий контракт:** сохранить семантику «либо весь импорт, либо ничего». Для крупных операций обеспечить прогресс, отмену до финального commit, предсказуемый UI. Не превращать одну атомарную операцию в частично видимые записи без staging-механизма.

**Приёмка:** ошибка на поздней строке, отмена и завершение процесса не оставляют частичного импорта; UI отображает прогресс и не выглядит зависшим; сохраняются версии/индексы/журнал согласованно.

## 3. Принятые правила и статус реализации

### F-01 · P1 · История версий и LWW

Следовать текущей модели спецификации v4.0: версия **при явном успешном сохранении формы** (создание/правка/восстановление), не при вводе символов и не при быстрых действиях. Дубликаты и неизменённое сохранение не создают версии. История синхронизируется, проигравшая конкурентная **явно сохранённая** редакция остаётся в истории; ручного разрешения конфликтов нет. LWW с HLC применяется только к текущему объекту.

Логический набор истории — **Top-20 неизменяемых версий по (HLC, ID)**, без возрастной очистки. Ротация и монотонные маркеры реализованы и проверены между независимыми SQLite; интеграция с полным протоколом и архивом остаётся открытой. У всех синхронизированных устройств итоговый набор и текущая запись совпадают. Быстрые действия не создают пользовательских версий, но являются обычными изменениями для синхронизации.

**Продолжение F-01 16.11.2026:** API восстановления удерживаемой версии атомарно создаёт новую актуальную запись/версию/HLC/журнал/индексы, не меняя старые снимки. Проверяется ожидаемый HLC и актуальная схема; новые defaults и более поздние значения не подмешиваются. Снимок до переноса во внешнюю коллекцию возвращает запись во «Входящие» с прежним UUID/исходными датами. Отказ удалённой цели, чужой/очищенной/вытесненной версии, сохранение Top-20 и откат при ошибке change_log покрываются Node/Rust DB-контрактами. UI подключён следующим блоком; полный локальный протокол остаётся отдельным шагом.

**UI истории:** отдельная страница записи показывает удерживаемые снимки, дату сохранения и исходную коллекцию; неизвестные/секретные значения скрыты до раскрытия. Явное восстановление использует ожидаемый HLC, обновление истории перечитывает текущее состояние перед повтором. Очистка конкретной записи и всех версий из главного конструктора требует явного подтверждения. Playwright проверяет отсутствие записей при просмотре/Back/отмене, одну новую версию восстановления, сохранность текущих данных после очистки/перезапуска и stale restore. Добавлены Android/Tauri-сценарии и общий API-контракт на Capacitor; Tauri и общий Rust-контракт прошли CI `0634263`, Android — `85b608e`. Проверка длинного Markdown выявила усечение снимка общим списочным форматтером до 200 символов: история теперь показывает полный исходник как безопасный текст; регрессия проверяет завершающий абзац и отсутствие исполняемых HTML-узлов. Полный локальный sync-протокол остаётся открытым.

### F-02 · P1 · Подготовка и отправка пакетов при сворачивании

**Не полагаться на упаковку/шифрование при событии `pause`.** В Android WebView асинхронная JavaScript-операция после сворачивания может не завершиться; «синхронно собрать пакет» в обработчике паузы не даёт гарантии.

Во время активной работы готовить компактные зашифрованные пакеты из уже сохранённых изменений **без отправки письма после каждого сохранения** — допустимо короткое отложенное формирование пачки после периода без правок. Отправлять при открытии, по кнопке, каждые 15 минут активной работы, а при сворачивании передавать **уже подготовленные** пакеты нативной разовой задаче (Android WorkManager). Хвост, не успевший войти в подготовленный пакет, сохраняется в SQLite и уйдёт позже. Не обещать доставку при принудительной остановке и не держать постоянный фон.

Проверять границы пакетов, nonce для AES-GCM, идемпотентность, очереди, повторные попытки, ошибку/квоты WorkManager и отключённую синхронизацию.

### F-03 · P1 · Локальный импорт, подключение и длительный офлайн

- Первоначальный запуск: **создать независимую базу или импортировать локальный архив**. Почта и сеть не обязательны.
- Подключение ещё одного устройства: импорт актуального локального архива и передача ключа синхронизации по QR/внешнему защищённому каналу. `dataset_id` остаётся у общей базы; у новой установки — новый `device_id`.
- **Автоматической начальной пересылки всей БД через почту нет**. «Экспорт/Импорт БД» — локальные операции пользователя, а не сообщения SMTP/IMAP.
- Если не хватает необходимых дельт, состояние расходится или устройство отсутствовало **90 и более дней**, поставить обмен на паузу. Предложить: (а) заменить местную базу актуальным архивом другого устройства; (б) продолжить как независимую базу, с новым `dataset_id`. Не выполнять автоматическое слияние двух длительно расходившихся баз.
- До замены базы **предложить экспорт текущей**. Отказ от предварительного экспорта не отменяет замену, но требуется ясное подтверждение потери локальных несинхронизированных правок.
- **Смена почтового адреса или `device_id` не лечит расхождение состояний.** Не использовать их как скрытый обход проверки. После восстановления корректно установить точку продолжения обмена и новую идентичность установки.
- Транспортное состояние, актуальность архива и курсоры должны позволять не пропустить дельты между экспортом и подключением. Если корректность нельзя обеспечить, приостановить синхронизацию и показать диагностируемое состояние, не гадать.
- Устройства с одним адресом не объединять без ключа. Секреты — в защищённом хранилище ОС; синхронизация всегда E2EE.

### F-04 · P2 · Реестр устройств

Переустановка порождает новый `device_id`; отображаемое имя редактируемо. Реализовать «Забыть устройство» (скрыть/деактивировать как участника) и отдельно «Отозвать доступ» (исключить и переиздать ключ для оставшихся устройств). Старые ID могут сохраняться в минимальных технических метаданных для распознавания исторических пакетов. UI-реестр показывать только при настроенной синхронизации; без синхронизации программа работает полноценно.

### F-05 · P1 · Длинные операции и возобновляемость на Android

- Перестройка индексов/FTS: короткие транзакционные порции с сохраняемым прогрессом; исходные данные — источник истины.
- Приём пакетов: каждый пакет применяется идемпотентно; данные, версии, локальные индексы/курсоры фиксируются согласованно. Прерванный пакет безопасно повторяется; уже зафиксированный повторно не применяется.
- Большой импорт/восстановление: staging, проверки формата/хешей, завершение без частично видимого набора данных; перед заменой — предложенный экспорт.
- Файлы: потоковое копирование, относительные имена, SHA-256, контроль пропавших/осиротевших файлов, временные файлы и атомарное завершение.
- Краш или переход Android WebView в паузу не должен оставлять «успешно завершённое наполовину». Не дублировать всю бизнес-логику на Kotlin/Rust ради фонового исполнения.

### F-06 · P1 для Android UX · Черновики только создания (изменено 15.11.2026)

**Изменение 0.6.0:** реализованы локальные файлы, debounce/close/lifecycle, восстановление только при создании, изоляция редактирования и удаление только после успешного Save. Добавлены unit/DB/Playwright и Android/Linux process-restart сценарии; Android/Linux приёмка подтверждается отдельно результатом CI. В 0.8.0 подключены пресеты: черновик проверяется раньше пресета, поэтому несовместимый пресет не мешает восстановлению ввода; добавлен мобильный UI-тест. Нативная приёмка профилей/пресетов и исправления гонки метаданных прошла на `be5d6b4`: https://github.com/Hemlig371/tessera/actions/runs/43723096820.

**Новые согласованные правила заменяют прежний F-06:** черновики используются **только при создании новой записи**, включая быструю форму и пресеты; редактирование существующих записей их не создаёт, не восстанавливает и не меняет.

- Один локальный черновик на коллекцию. Сохраняется после паузы ввода ~3 с, при сворачивании и по возможности при обычном закрытии. Поля «Секрет» исключить; никаких `records`, пользовательских версий, `change_log` и синхронизации черновика.
- При очередном **нажатии создания в той же коллекции** открывается стандартная форма создания с восстановленными значениями, без отдельного диалога/менеджера. Не открывать его при одном лишь входе в библиотеку или коллекцию. Открытие другого места не заменяет черновик.
- «Закрыть», системный «Назад» и навигация **сохраняют** черновик. **Только успешное «Сохранить»** создаваемой записи удаляет его. Ошибка валидации или сохранения черновик оставляет.
- Быстрые формы/пресеты не имеют права молча затереть восстановленный ввод. При изменении схемы неизвестные значения сохраняются и несовместимость показывается; не пытаться сохранять существующую запись по устаревшему черновику.
- Сохранение при мгновенном убийстве до debounce не гарантирует последние символы. Не вводить «Удалить черновик», «Начать заново» или самостоятельную систему пользовательских черновиков.

**Приёмка:** Android emulator pause/kill/relaunch, обычное закрытие и возврат в ту же коллекцию, создание в другой коллекции, новая/быстрая форма и пресет, отсутствующие секреты и события записи, удаление только при успешном сохранении, отсутствие влияния на редактирование. Тесты старого поведения «Отмена удаляет черновик» обновлять при внедрении, не маскировать конфликт пропуском проверок.

### F-07 · P2 · Формулы, агрегаты, Decimal и запросы

Decimal с максимум 5 знаками, без бинарной арифметики денег; Excel-подобные формулы с `NULL`-семантикой, диагностируемыми ошибками и обнаружением циклов. Агрегаты по 1→N и обратным связям. Сохранить возможность **сортировки/фильтрации/группировки по формулам**: простые выражения — SQL/производные значения; сложные зависимости — локальный кэш с инвалидацией. Не синхронизировать вычисленный кэш. `NOW()` зависит от локальных системных часов и требует пересчёта; не выдавать устаревшее значение за постоянное. Технические UTC/HLC и пользовательское локальное время не смешивать.

### F-08 · P2 · Почтовый ящик и управление транспортом

Почта — **необязательный транспорт**, а не идентичность базы. Для синхронизации рекомендуется выделенный ящик. ## 7. Дополнения: согласованные решения перед продолжением реализации

Решения подтверждены пользователем 16.11.2026. Они уточняют реализацию и критерии приёмки, но **не отменяют и не урезают функциональные требования v4.0**.

### D-01 · История Top-20 — согласовано
**Реализация ядра 16.11.2026:** явные сохранения атомарно ротируют `record_versions`; watermark отсечения и per-record/global маркеры очистки хранятся в `app_meta`. Объединение Top-20 проверяется на независимых SQLite, с перестановками, дублями, HLC ties, старыми пакетами и очисткой; remote HLC учитывается перед следующим локальным сохранением. Существующий избыточный набор сжимается возобновляемыми транзакциями при открытии. Локальные UI истории и восстановление версии реализованы (F-01); готовность полного sync-протокола этим не подтверждается.

- Для каждой записи автоматически поддерживать последние 20 версий по детерминированному порядку `(HLC, стабильный ID версии)`.
- Версии за пределами Top-20 вытесняются автоматически; календарный возраст сам по себе не является критерием хранения.
- Правило одинаково для всех устройств и не зависит от порядка доставки. Поздняя старая версия не должна вытеснять более новую.
- Отдельная ручная очистка истории сохраняет предусмотренный спецификацией синхронизируемый маркер.
- **Приёмка:** более 20 версий, одинаковый Top-20 при разных порядках/дублях доставки, отставшее устройство, повтор пакета, ручная очистка и отсутствие «воскрешения» очищенной версии.

### D-02 · Жизненный цикл change_log — согласовано
- При выключенной или ещё не настроенной синхронизации транспортный журнал не должен расти без ограничений. До первичного подключения допустимо не создавать избыточные события либо безопасно компактизировать их: исходная точка синхронизации строится из актуальных таблиц.
- При `active` сохранять события, пока не доказано, что они больше не нужны ни одному подключённому устройству.
- При `paused` не сбрасывать очередь и не терять дельты; возобновление должно продолжаться с согласованного состояния.
- `detached` — отдельный набор данных с новым `dataset_id`; очищается только локальное протокольное состояние прежней группы, не пользовательские записи/версии.
- История версий, актуальные записи, change_log и экспорт БД имеют разные жизненные циклы.
- **Приёмка:** тысячи автономных сохранений без линейного роста избыточного журнала; первичное включение из текущего состояния; pause/resume; несколько устройств с разным прогрессом; безопасная компактация и восстановление после сбоя.
