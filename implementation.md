# Tessera v4.0 — реализация и подтверждённые проверки

**Состояние:** предрелизная реализация, автоматическая приёмка завершена; публикация и ручная приёмка реальных устройств/провайдеров не выполнялись. Версия исходников — `0.24.0`, Android `versionCode 25`. Целевое имя продукта — **Tessera v4.0**; текущая версия в package/build-конфигурациях не является опубликованным релизом.

**Контракты:** [функциональные требования](target-specification-v4.0.md) и [интерфейс](ui-specification.md). Этот документ описывает только фактическую реализацию, доказательства и ограничения, не заменяет требования. Правила сопровождения — [AGENTS.md](AGENTS.md), команды — [README.md](README.md).

## Реализованная система

- **Local-first:** Android (Capacitor/Kotlin), Windows/macOS и опционально Linux (Tauri/Rust), общие React/TypeScript/Vite, Zustand для UI, i18next, TanStack Virtual. Обязательного сервера, аккаунта или сети нет. Production браузерного SQLite/localStorage-fallback нет.
- **Данные:** `src/core/repository.ts` — единый публичный API и путь записи. Бизнес-правила, DDL/bootstrap, типы, формулы, HLC/LWW, история, журнал изменений и синхронизация — в общем TS-ядре. `src/platform/serial-database.ts` сериализует операции; Kotlin/Rust предоставляют платформенные SQLite/OS-адаптеры. UI не исполняет SQL. Текущая схема — `tessera-dev-bootstrap-2`, **без миграций между промежуточными dev-схемами**. Несовместимую БД нельзя молча сбрасывать.
- **Пользовательские возможности:** библиотеки, коллекции, типизированные поля и JSON-значения, связи, Markdown/«Входящие», формы и пресеты создания, локальные черновики только новых записей, профили отображения, фильтры, Kanban/календарь/дерево/сводки, Decimal и формулы, поиск/FTS, виртуализированные списки, история Top-20, корзина, быстрые действия, вложения, CSV, архивный экспорт/импорт с проверкой и восстановлением. Функции не требуют предметно-специфических таблиц.
- **Синхронизация только по согласию:** независимые SQLite, локальный протокол change journal/replay/ACK, baseline, LWW, tombstones, история, pause/resume/detach, защита от повторов и сбоев; AES-256-GCM для конвертов, квитанций и частей вложений. QR используется для сопряжения; Android — нативные SMTP/IMAP, Android Keystore и камера; desktop — системный TLS SMTP/IMAP и OS-хранилище секретов (Windows Credential Manager / macOS Keychain). Сообщение «отправлено» не означает «применено». Пароли/ключи не сохраняются в обычный архив.
- **Хранилище и перенос:** архив базы — **незашифрованный ZIP** с manifest/JSON/NDJSON и малыми оригиналами/хешами, для больших файлов — предусмотренные метаданные/заглушки; пользователь должен учитывать конфиденциальность. Нельзя копировать активный `.sqlite` без WAL-контекста. Android Storage Access Framework не гарантирует атомарность финальной записи внешнего ZIP: успех показывается после закрытия файла, неполный архив при импорте отвергается. Внешняя копия/восстановление — пользовательская операция; runtime recovery не заменяет backup.

QA-приложения имеют отдельные идентификаторы и базы; обычные установщики не содержат тестовый набор. QA-пакеты не подписаны для публичного релиза.

## Эксплуатационные условия

- Для разработки — Node.js **24.x**, Rust stable и нативные зависимости Tauri; для Android — JDK **21**, Android SDK/API **36** и Gradle wrapper. Сборки и команды подробно описаны в [README.md](README.md); фактические шаги CI — в [`.github/workflows/ci.yml`](.github/workflows/ci.yml).
- Windows dev-профиль `%APPDATA%\app.tessera.personal.dev` отделён от `%APPDATA%\app.tessera.personal`. Нельзя считать dev-схему совместимой с произвольной будущей/старой базой и нельзя делать автоматический destructive downgrade. Изменения после публичного релиза требуют версионированных миграций.
- Пакет `@capacitor-community/sqlite` закреплён на **8.1.1**; `npm ci` применяет checksum-проверенный идемпотентный lifecycle-патч через `scripts/patch-sqlite-lifecycle.mjs` для rollback/close на owner thread при WebView recreation. Обновление зависимости требует отдельной проверки этого контракта.
- `android/app/tessera-debug.keystore` — постоянный **публичный тестовый** сертификат (alias `androiddebugkey`, пароль `android`), **не релизная подпись**. Перед заменой APK с иной подписью следует сохранить внешний ZIP-архив, проверить его и только затем переустанавливать и импортировать. Не удалять данные пользователя ради обновления.
- Секретные поля маскируются, исключены из общего FTS/сводок/диагностики, но маскирование и Android UI-lock **не шифруют SQLite или экспортный ZIP**. Android lock опирается на системную авторизацию, собственного PIN нет. Реальные почтовые секреты — только в защищённых OS-хранилищах.
- Linux application/GTK native E2E не входит в принятую приоритетную матрицу. Наличие Linux путей в проекте не означает их полного подтверждения итоговым run.

## Ограничения и ручная приёмка перед публикацией

**Открытый test-only quarantine:** `scripts/desktop-e2e.mjs` исключает сценарий нативного GTK/Tauri save-picker для UI экспорта/замены архива. Покрытие Core archive/SQLite, Android replacement и native file/recovery не заменяет этот UI-путь. Сценарий требует ручной проверки или отдельного исправления и повторной проверки, а не удаления работающих data-тестов.

**Не подтверждено автоматической матрицей:** полноценный визуальный проход на физических Android WebView / Windows WebView2 / macOS WKWebView, все контрастные состояния, OEM энергосбережение и background/recreation, реальные SAF-провайдеры и Share/launcher, камера для QR, системные календарь/напоминания и `.ics` association, реальные IMAP/SMTP аккаунты и особенности OAuth/2FA/TLS/лимитов, долговременное offline-сопряжение, release-подпись Windows/macOS и notarization. Отдельный UI E2E именно для typed-formulas не был добавлен в Git; базовые формулы покрыты unit/DB. Это **пробелы доказательств**, не заявления о найденной ошибке бизнес-логики.

Рекомендуемая **ручная приёмка** — на тестовых данных и с явным разрешением для внешних аккаунтов:

1. Android: установка/обновление, экранные размеры, системная авторизация, WebView recreation, фон/OEM, Share, внешние SAF-папки, системные действия и QR-камера.
2. На отдельной тестовой БД: запись с изображением → внешний ZIP/manifest → изменение → импорт с подтверждением → сверка текста/файла после перезапуска; затем повреждённый ZIP (исходная БД не меняется). Перед сменой сертификата — проверенный внешний backup.
3. Windows/macOS: установка подписываемых впоследствии пакетов, реальные native WebView, файловые диалоги экспорта/замены и системные интеграции. При необходимости отдельно Linux GTK picker.
4. С разрешённым тестовым почтовым ящиком: pairing, TLS/auth, доставка/применение/ACK, повтор, отсутствие сети и возобновление, поведение провайдера; не применять реальные личные данные.
5. Доступность/визуальный осмотр: 390 px с 150% текстом, 1280 px, темы, длинные значения, клавиатура, loading/error, контрастность и навигация на целевых устройствах.

Релиз и release tags отсутствуют. Решение о публикации принимается после отдельной ручной проверки, а не из одного зелёного CI.
