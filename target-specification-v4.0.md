# Целевая спецификация приложения — v4.0

**Дата:** 14 ноября 2026 г.  
**Статус:** спецификация для реализации и приёмочного тестирования.  
**Основа:** целевая спецификация v3.2 и последующие согласованные решения.  
**Правило приоритета:** требования настоящего документа имеют приоритет над прежними редакциями.  
**Тип продукта:** личная универсальная база данных, local-first, Android-first.

**Согласованные дополнения 15 ноября 2026:** именованные профили отображения одной коллекции, пресеты создания, черновики только создания, расширенный перенос «Входящих» и отдельные требования интерфейса в [ui-specification.md](ui-specification.md). Это изменения целевого контракта, **не утверждение, что функциональность уже реализована**. Версия приложения на момент согласования — 0.5.0; существующие миграции 1–5 неизменны. [Аудит](audit.md) остаётся обязательным перечнем рисков и приёмки. Основная спецификация задаёт бизнес-правила, UI-документ — интерфейс; при противоречии нельзя молча ослаблять корректность или сохранность данных.

## 1. Назначение, границы и принципы

Приложение позволяет без программирования собирать личные мини-приложения — **библиотеки** с **коллекциями**, настраиваемыми полями, формами, карточками записей, списками и сводками. Пользователь быстро сохраняет неструктурированную информацию во **«Входящих»** и при необходимости переносит её в коллекции. Все основные функции работают **без сети, аккаунта и синхронизации**.

### 1.1. Неизменные требования

1. **Android — основная платформа**, включая полноценный конструктор библиотек, полей и интерфейсов. Desktop: Windows x64, macOS ARM64, Linux x64 (AppImage). iOS и публичная веб-версия не нужны.
2. Одна и та же бизнес-логика работает на всех платформах. Устройство может вести полностью независимую базу без почты.
3. Источник истины — локальная SQLite. Приложение не требует собственного сервера, внешней облачной базы или платной службы.
4. Синхронизация **необязательна**, включается пользователем; при её включении через SMTP/IMAP идут только аутентифицированные зашифрованные пакеты. Почтовый сервер видит метаданные доставки, но не пользовательское содержимое.
5. Пользовательская структура и данные имеют стабильные ID; названия и порядок полей можно менять без потери данных.
6. Архитектура готовится к финальному функционалу с первого этапа; допускается постепенное открытие UI-возможностей. Не делать одноразовый демонстрационный прототип на `localStorage`.
7. Приложение не держит постоянный процесс в фоне, не создаёт собственную очередь системных напоминаний, не содержит Android-виджетов и не предоставляет многопользовательских ролей.
8. Формат данных и экспорт документированы; CSV импортируется и экспортируется по коллекциям. Автотесты и бенчмарки живут **в dev/CI**, а не в пользовательском бинарнике.
9. В пользовательском интерфейсе не показывать служебную сложность синхронизации без необходимости. Ошибки и невозможные операции отображать понятно; не утверждать об успешной отправке до её фактического выполнения.

### 1.2. Вне области проекта

- Собственный менеджер паролей, SQLCipher, локальное криптографическое шифрование `app.sqlite` и отдельных библиотек.
- Обязательная непрерывная синхронизация и фоновый процесс для неё.
- Автоматическая двусторонняя синхронизация с системным календарём, собственные push-/alarm-уведомления.
- Коллаборация нескольких пользователей; сервис авторизации; веб-сервис хранения.
- Ранее исключённый отдельный пользовательский объект «Представление» поверх коллекции в исходном смысле. **Новые именованные профили отображения одной коллекции (§4.2) — не та исключённая сущность:** это сохранённые конфигурации списка/режима/фильтров над теми же записями, без собственного набора данных.
- Исполнение произвольного пользовательского JavaScript или Excel-макросов.
- Автоматическое слияние **независимых** наборов данных либо баз, долго работавших без пригодной истории доставки.

## 2. Стек, платформы и архитектурные границы

| Слой | Решение |
|---|---|
| UI | React + TypeScript + Vite |
| Состояние UI | Zustand; только навигация, формы, сессия и отображение; записи — в SQLite |
| Списки | TanStack Virtual, ограниченные SQL-выборки, постраничная загрузка |
| Общее ядро | TypeScript: модель, валидация, запросы, связи, формулы, история, HLC, синхронизация и криптографический протокол |
| Android | Capacitor; стандартные/готовые плагины, при необходимости узкие Kotlin-адаптеры |
| SQLite Android | Сначала **`@capacitor-community/sqlite`**, принять после проверки FTS5, JSON, WAL, индексов по выражениям, транзакций; собственный плагин только при доказанном ограничении |
| Desktop | Tauri 2; тонкий Rust-слой; `rusqlite` для SQLite |
| Dev на Windows | `tauri dev` с **реальным SQLite**, не имитацией или `sql.js` |
| Тестовое ядро | Нативная SQLite в Node/тестовом раннере; одинаковые SQL-правила, контрактные тесты адаптеров |
| Транспорт | SMTP/IMAP через Kotlin/Rust-адаптеры; почтовый код не содержит бизнес-правил |
| Crypto | WebCrypto AES-256-GCM в общем TS-ядре; secure credential storage через ОС |

Платформенные адаптеры: `DatabaseAdapter`, `FileAdapter`, `TransportAdapter`, `ExternalActionsAdapter`, `SecureCredentialsAdapter`, `PlatformLifecycleAdapter`. Интерфейсы должны допускать подмену в тестах. **Не дублировать бизнес-логику** на Rust и Kotlin.

**Приёмка SQLite на Android:** через настоящий bridge выполнить `sqlite_version()`, `json_valid`/`json_extract`, создание и запрос FTS5, индекс выражения, параметризованный запрос, транзакцию с rollback, WAL/checkpoint. В сборке запускать дешёвую проверку совместимости; обширные тесты — только в dev/CI. Отсутствие требуемых возможностей — блокирующая ошибка адаптера.

**Оптимизация:** никакого полного чтения коллекции в React ради сортировки; выборки с лимитом; подготовленные/параметризованные запросы; курсорная пагинация со стабильным вторичным ключом `id`; миниатюры отдельно от оригиналов; вычисления и индексация не должны надолго блокировать UI. Тяжёлые ORM и универсальные конструкторы не вводить заранее.

## 3. Физическое хранение и техническая модель

### 3.1. Каталоги

```text
<private-app-data>/
  databases/app.sqlite
  attachments/<prefix>/<attachment-id>
  cache/thumbnails/
  operational/outbox/
  operational/inbox/
  operational/drafts/
  operational/logs/
```

На Android — приватный каталог приложения. На Windows/macOS/Linux — штатный пользовательский каталог данных. В SQLite — относительные идентификаторы, **не абсолютные пути**. Вложения — отдельные файлы, не BLOB. Все пути нормализуются; пользовательский текст не используется как компонент рабочего пути.

### 3.2. SQLite c JSON-значениями

База — одна `app.sqlite`. **Одна таблица `records`** содержит `data` — валидный JSON-объект «ID поля → типизированное значение». Модель пользовательских коллекций документная; не создавать таблицу на каждую коллекцию. Служебные таблицы остаются реляционными.

| Таблица | Назначение |
|---|---|
| `app_meta` | `dataset_id`, версии схемы и формата, локальные флаги и состояние инициализации |
| `libraries` | Название, оформление, стартовый экран, порядок, настройки UI-блокировки |
| `collections` | Библиотека, системные параметры, основное и входящее поля, правила списков |
| `fields` | ID, коллекция, тип, правила, значения выбора, параметры индекса и отображения |
| `records` | ID, collection ID, JSON data, даты, HLC, device ID, удаление/надгробие |
| `relation_index` | Перестраиваемые прямые/обратные рёбра |
| `ui_configs` | Существующие независимые настройки формы, карточки и списка; сохранять совместимость |
| `quick_forms` | Уже реализованные самостоятельные конфигурации быстрых форм (миграция 5) |
| `collection_display_profiles` (рабочее имя) | Новые именованные профили отображения, порядок, настройки списка, фильтра, итогов и режима; миграция после v5 |
| `creation_presets` (рабочее имя) | Пользовательские пресеты создания записей с предзаполненными полями и выбором формы; миграция после v5 |
| `dashboards`, `dashboard_widgets` | Сводки библиотек |
| `attachments` | ID, record ID, имя, MIME, размер, SHA-256, наличие локальной копии |
| `attachment_locations` | Метаданные известных устройств, на которых файл есть/был доступен |
| `record_versions` | Неизменяемые версии явных сохранений, синхронизируемые |
| `change_log` | Локальные события для формирования дельт, технический журнал |
| `sync_devices`, `sync_state`, `sync_inbox_state`, `sync_outbox_state` | Устройства, номера пакетов, интервалы/состояния приёма и отправки |
| `sync_rejected`, `sync_missing` | Изолированные некорректные пакеты/информация о пропусках |
| `app_settings` | Общие синхронизируемые настройки |
| `local_settings` | Платформенные настройки, разрешения, локальные пути и флаги |
| `schema_migrations` | Версионированные миграции |
| FTS5 и производные индексы | Локальный поиск и ускорение запросов, пересоздаваемы |

Служебные имена — ориентир для реализации; точное SQL DDL находится непосредственно в миграциях репозитория и является машинно проверяемой частью спецификации. Индексные имена генерируются по стабильным техническим ID. Для всех синхронизируемых объектов предусмотрены `id`, `hlc`, `device_id`, `deleted_at`/`purged` в применимой форме.

**Инварианты:**

- Каждая локальная правка синхронизируемого объекта и соответствующая запись `change_log` фиксируются **в одной транзакции**; при выключенной синхронизации допускается накопление только минимально необходимого журнала либо его безопасная компактация.
- Обновление/применение пакета, курсора и текущего состояния атомарно. Сбой не оставляет «курсор продвинулся, а данные не применены».
- Неизвестные ID полей и их JSON-значения не удаляются при приёме синхронизации; запись без ещё не полученного описания коллекции откладывается.
- Переименование поля меняет каталог, не JSON-ключ. Удаление поля мягкое; смена типа допускается только с проверенным преобразованием, иначе создать новое поле и перенести значения явно.
- Параллельные обращения к SQLite идут через единый последовательный writer/транзакционный адаптер; на desktop не должно быть двух независимых экземпляров приложения с собственной логикой записи одной базы.

### 3.3. Поиск и индексы

1. Системные индексы для ID, `collection_id`, `deleted_at`, `hlc`, служебных курсоров.
2. Простые поля индексируются вручную флагом **«Индексировать»** (по умолчанию выключен) или автоматически, если заданы в постоянной конфигурации сортировки, фильтра или группировки коллекции. Когда поле более не требуется и пользовательский флаг снят — индекс можно удалить. Фоновые операции индексации выполняются небольшими порциями/без длительной блокировки UI.
3. Для JSON применять выражения `json_extract` с точным соответствием запросов и выражений индексов. Decimal сортируется по корректному числовому ключу, **не лексикографически**. Индексируемые `NULL` и отсутствие поля обрабатываются одинаково по правилам типа.
4. **FTS5 — отдельно от обычных SQL-индексов.** По умолчанию поиск включён для основного текстового поля и текстовых/Markdown-полей; пользователь может включить или выключить его в настройках поля. Настраивать индексацию текста при создании каждой коллекции **не обязательно**. Поле «Секрет» исключено без возможности включения.
5. Глобальный поиск, поиск внутри библиотеки и коллекции. Для русского языка в первой версии: Unicode-aware регистр, префиксный поиск; морфологические формы слов не гарантируются. Сортировка русских строк использует нормализованные Unicode/locale-aware ключи, не один SQLite `NOCASE`.
6. Индексы и FTS5 локальны, не синхронизируются. После импорта/восстановления могут быть пересозданы.
7. `EXPLAIN QUERY PLAN` и проверка корректности планов — в автоматических dev/CI-тестах.

## 4. Библиотеки, коллекции, записи

### 4.1. Библиотеки

Логически независимые мини-приложения с названием, иконкой, цветом, порядком, коллекциями и сводкой. При обычном запуске показывать все библиотеки; Android-ярлык может открыть конкретную библиотеку по ID. Стартовый экран библиотеки настраивается: список/карточки коллекций, сводка, конкретная коллекция или её именованный профиль, либо последний экран. Удалённая стартовая цель безопасно переключается на каталог коллекций. Межбиблиотечные структурные связи не предусмотрены, системные «Входящие» и глобальный поиск общие.

**«Блокировка библиотеки»** — UI-функция от случайного доступа, по возможности с биометрией/системной авторизацией; не шифрует SQLite. Скрываются предпросмотры и чувствительные экраны в recent-apps там, где ОС поддерживает. Приложение не является менеджером банковских паролей.

### 4.2. Коллекции и настройки UI

Каждая коллекция независимо задаёт:

- **Форму:** порядок/группы полей, видимость, обязательность, подсказки, значения по умолчанию, правила; визуальная компоновка по строкам с 1–3 колонками и адаптивным переносом на узком экране.
- **Карточку:** независимую компоновку, действия, файлы, обратные связи, блоки связанных записей.
- **Именованные профили отображения коллекции** («Представления» в UI): собственные название, стабильный ID, порядок, режим, состав/расположение полей, фильтры, сортировка, группировка, быстрые действия и итоги. Один профиль выбирается по умолчанию; создавать можно произвольное число. Сами записи одни и те же; профили не создают отдельной коллекции или пользовательского объекта поверх данных. При миграции существующая одиночная настройка списка становится профилем по умолчанию **без потери компоновки**. Новая коллекция начинает со списка.
- **Режимы профиля:** строки, карточки, таблица, Kanban, календарь, дерево, Гант, граф при применимости; доступные режимы задаются для конкретной коллекции, реализуются поэтапно. Поддерживать относительные условия («Сегодня», «Неделя») по локальной дате, а не запоминать вычисленный день в фильтре.
- **Быструю форму:** подмножество полей с заполнением остальных значениями по умолчанию.
- **Пресеты создания:** именованные сочетания предзаполненных значений (в том числе вычисляемых текущей датой) и выбора обычной/быстрой формы. Не являются записями; проверяются по актуальным правилам полей при создании. Короткое нажатие контекстного `+` открывает назначенную по умолчанию форму, дополнительные варианты доступны через видимую стрелку и долгий тап/ПКМ.

Ранее исключённая концепция отдельного пользовательского объекта «Представление» **не возвращается**: описанные выше профили — только конфигурации отображения **одной** коллекции, не хранящие собственные данные. **Сводка библиотеки** — независимый редактируемый экран с метриками, диаграммами, списками, быстрыми действиями и календарными блоками; виджеты могут использовать формулы и фильтры выбранного профиля либо собственный фильтр. Итоги вычисляются по всем подходящим записям, не только загруженной странице.

В мобильном конструкторе полноценные настройки доступны с Android; на desktop тот же функционал с адаптированной компоновкой. Дизайн/иконки/отступы выбираются итеративно, функциональная доступность не урезается.

### 4.3. Жизненный цикл записи

- ID стабильный UUID, служебные `created_at`, `updated_at` (UTC), `created_local`, `updated_local` (локальное значение как видел автор), `deleted_at`, `hlc`, `device_id`.
- Создание/редактирование происходит в UI-форме, в памяти до явного **«Сохранить»**. Ни одно нажатие клавиши не меняет `records`, историю или `change_log`.
- «Сохранить» проверяет типы, ограничения, нужные связи и формулы/правила, затем атомарно создаёт запись/обновляет её, версию, `change_log` и производные данные. Сохранение без изменений не создаёт версию.
- При **редактировании существующей** записи «Отмена» закрывает форму без сохранения и может запросить подтверждение ухода. При **создании новой** записи «Закрыть» не создаёт запись, но сохраняет локальный страховочный черновик согласно §4.4; никакого подтверждения из-за несохранённого ввода не требуется. Не вводить термин «Отбросить». Пресеты и быстрые формы не обходят явное сохранение.
- Быстрые действия (галочка, кнопки счётчика, смена статуса без открытия формы) сохраняются **сразу** и синхронизируются, но **не создают пользовательских версий**.
- Обновления индексов, получение одинакового состояния по сети, вычисление формул и открытие карточки не создают пользовательской версии.

### 4.4. Локальные страховочные черновики создания на Android

Назначение — сохранить незавершённое **создание новой записи** как при сворачивании/краше, так и при обычном закрытии формы. Это не альтернативный способ сохранения записи и **не** страховка от несохранённого редактирования существующих записей.

- Ровно **один** активный локальный черновик создания на пару `library_id/collection_id`, включая создание через быструю форму и пресет. Для редактирования уже существующих записей черновики не создаются, не открываются и не меняются.
- Во время ввода запись черновика выполнять после паузы ~3 с (debounce), дополнительно по возможности при сворачивании/неактивности и при обычном закрытии формы; **не** писать каждый символ. Секретные поля не записывать. Хранение — локальный несинхронизируемый оперативный файл; не `records`, не пользовательская версия, не `change_log`.
- Кнопка создания в соответствующей коллекции открывает **обычную форму создания** с восстановленными значениями черновика, без промежуточного экрана или сообщения о восстановлении. Не открывать чужой черновик при переходе в другую коллекцию и не показывать его автоматически при входе на главную страницу приложения.
- «Закрыть», системный возврат или переключение экранов **не удаляют** черновик; отдельные команды «Удалить черновик», «Начать заново», «Управление черновиками» не требуются. **Только успешное явное «Сохранить» создаваемой записи удаляет** соответствующий черновик. Ошибка сохранения оставляет его доступным.
- Запуск быстрой формы/пресета при существующем черновике не перезаписывает введённые значения; приоритет у восстановленного ввода, дополнительные defaults применяются только без потери данных.
- При изменении схемы пока черновик хранится неизвестные значения сохранить, а несовместимость показать при открытии. Не допускать молчаливого стирания.
- Не гарантировать последние символы при мгновенной гибели процесса до срабатывания debounce/события lifecycle; это принятое ограничение. Для Android обязательны эмуляторные проверки pause/kill/relaunch и обычного закрытия/открытия.

### 4.5. «Входящие»

Глобальный системный контейнер для произвольного текста/Markdown, ссылок и вложений без обязательного выбора библиотеки/коллекции. Ручной захват — одно простое поле (в том числе Markdown) с явным сохранением и обычными правилами черновика создания. Каналы: глобальное `+`, Android Share `ACTION_SEND`/`ACTION_SEND_MULTIPLE`, голосовой ввод системными средствами. **Android Share — явное исключение:** выбор Tessera через системное «Поделиться» означает непосредственное сохранение новой записи во «Входящих» без второй формы, с возвратом в исходное приложение; при ошибке нельзя выдавать ложный успех.

При создании коллекции назначается **целевое текстовое поле для входящего содержимого**; расширенная настройка приёмной коллекции может сопоставить Markdown-заголовок и остальное тело с отдельными целевыми полями. При отсутствии корректного многополевого маппинга сохранять всё исходное содержимое в назначенном входящем поле. Перенос требует выбора библиотеки/коллекции, при необходимости заполнения остальных обязательных полей и явного сохранения. Не терять нераспознанный текст при разборе Markdown; невозможное сопоставление должно приводить к безопасной ошибке/предпросмотру, а не потере данных. Сохраняются ID записи, даты и вложения; меняется `collection_id` и структура `data` в одной транзакции. Перенос не создаёт дубликат в корзине. Если пользователь отменяет форму, исходная запись остаётся во «Входящих».

### 4.6. Связи

Поле «Связь» указывает на одну или несколько записей целевой коллекции **в той же библиотеке**. В JSON сохраняются ID/список ID; `relation_index` — перестраиваемый обратный индекс. Карточка может показывать обратные ссылки, связанные элементы и кнопку создания связанной записи. При удалении цели ссылка остаётся как отсутствующая/удалённая, не удаляя исходную запись. `[[ссылка]]` в Markdown позже разрешается в ID записи и безопасно отображается; название — только визуальная подпись.

| Категория | Типы / виджеты |

| Числа | Целое, Decimal, денежное поле; счётчик `−/+`, рейтинг, прогресс, слайдер — варианты UI |
| Логические | Чекбокс, переключатель |
| Выбор | Один/несколько вариантов со стабильными ID вариантов |
| Время | Дата, время, локальные дата+время, диапазон дат, длительность |
| Ссылки | Связь с одной/многими записями, прямые и обратные |
| Файлы | Файл, изображение, несколько вложений |
| Дополнительно | Адрес/координаты, цвет/иконка, структурированный JSON (по необходимости) |
| Системные | Формула, агрегат, поле «Секрет» (UI-маскирование без шифрования) |

Тип хранения, UI-контрол и формат отображения независимы. «Напоминание» не тип поля. Поля «Секрет» не допускаются в FTS, глобальном поиске, общих списках/сводках, шаблонах сообщений и диагностических логах; значения в обычной SQLite/открытом экспорте **не зашифрованы**.

### 5.1. Время

- Пользовательские `date`, `time`, `local_datetime` сохраняются буквально (ISO без TZ), **не пересчитываются** при показе на другом устройстве.
- Отдельные `created_local`/`updated_local` отражают локальные часы устройства в момент действия; `created_at`/`updated_at` — технический UTC timestamp. Для сортировки операций и LWW используется HLC, а не строка локального времени.
- HLC состоит из физического UTC-времени, логического счётчика и уникального `device_id`; он монотонен локально. Расхождения системных часов — принятое ограничение. **Не предупреждать о часовом сдвиге и не отклонять пакеты из-за произвольного порога.**
- `NOW()` возвращает локальное текущее время устройства и при чтении/отображении пересчитывается. Его результат не фиксируется как синхронизируемый результат формулы.

### 5.2. Decimal и деньги

- Пользовательское дробное значение — до **5 знаков** после запятой, округление `half-up`, до сохранения UI показывает округлённый результат. Числовое поле не становится текстовым при вводе длинного числа. Очень длинный код/номер пользователь вводит в **текстовое** поле.
- JSON хранит нормализованную десятичную строку; арифметика ядра выполняется Decimal, а не через бинарное округление `Number`. Промежуточные вычисления имеют достаточную точность, округление на границе сохранения/отображения.
- Для сортировки, сравнения и индексов нужен масштабированный целочисленный либо другой точный числовой ключ с проверенным диапазоном; арифметика и индексы не должны переполняться молча.
- Денежное поле — тот же Decimal с числом знаков отображения (обычно два) и **символом валюты как форматом**, без конвертации валют.

## 6. Формулы, зависимости, агрегаты

Ограниченный **Excel-подобный синтаксис**; формулы хранят стабильные ссылки на ID полей/связей и не содержат пользовательский JS. UI-редактор на телефоне поддерживает выбор поля/функции, подсказки и предварительный результат.

- Арифметика `+ − × ÷`, скобки, сравнение, `IF`, `AND`, `OR`, `NOT`, `SUM`, `AVERAGE`, `COUNT`, `COUNTA`, `MIN`, `MAX`, `ROUND`, базовые текстовые операции, `DATE`, `YEAR`, `MONTH`, `DAY`, `NOW`.
- Агрегаты действуют на списки связанных записей и **обратные связи** (пример: сумма стоимости позиций покупки, сумма калорий дневника, количество задач проекта), не только 1:1.
- `NULL` не учитывается в `SUM`/числовом `COUNT`/`AVERAGE`, явный `0` учитывается; `COUNTA` считает непустое, включая текст. Для пустого набора `SUM=0`, `COUNT=0`, `AVERAGE=NULL`.
- Деление на ноль, несовместимые типы, отсутствующая обязательная ссылка и циклы зависимостей возвращают **явную ошибку**, видимую в UI.
- Движок детектирует циклы по графу зависимостей. При изменении связанной записи зависимые формулы помечаются устаревшими.
- Результаты формул **не синхронизируются**. Простые формулы вычисляются по значениям текущей записи; для сортировки, фильтрации и группировки по формулам поддержать локальные производные значения/кэш с инвалидацией. Формулы со связями рассчитывать через индекс связей и кэш. Если выражение зависит от `NOW()`, не обещать постоянно актуальный индекс: при запросе пересчитывать либо явно ограничить индексирование динамической формулы без лишения возможности просмотра.
- Сводки и итоги считают **все подходящие записи**, а не только видимые строки. Отсутствие кэша влияет на скорость, но не на правильность ответа. Формулы используют ограниченные безопасные функции; исполнение JS/SQL строк пользователя запрещено.

**Итоги профилей и сводок:** формульные агрегаты и списки используют все записи, подходящие под фильтр профиля или отдельный фильтр виджета, включая динамические условия даты. Суммирование по одной загруженной странице недопустимо.

## 7. История версий, быстрое редактирование и корзина

### 7.1. Синхронизируемая история

1. Явное создание записи, её содержательное сохранение через форму и восстановление старой версии создают **неизменяемую версию** с UUID, записью, JSON-состоянием, HLC, `device_id` и локальной датой сохранения. Неизменённое сохранение не создаёт версию.
2. Быстрые одношаговые действия не создают пользовательской версии, но обновляют актуальную запись и журнал синхронизации.
3. История синхронизируется, объединение версий идёт **по ID**; LWW применяется к **текущей записи целиком**, а не к истории. Проигравшая явно сохранённая конкурентная версия входит в историю. Ручного интерфейса разрешения конфликтов нет.
4. **Top-20:** на каждом устройстве пользовательская история содержит 20 версий с максимальным `(HLC, version_id)`; время жизни не ограничено. Поступившие старые версии, не входящие в глобальные Top-20, не отображаются и не удерживаются после безопасной обработки.
5. Требование сходимости: при получении одного и того же множества версий все устройства имеют один и тот же набор последних 20. **Top-20 объединения вычисляется по Top-20 частей**, поэтому для обмена достаточно доставлять текущие наборы/новые объекты, а не весь архив бесконечной истории.
6. Для предотвращения возврата старой версии при поздней доставке хранить достаточный технический маркер отсечения/проверки дубликатов; правила не должны нарушать сходимость. Технические маркеры не считаются пользовательскими версиями.
7. Восстановление версии — новое **явное сохранение**, новая актуальная запись и новая версия, передаваемая синхронизацией.
8. Вложения в истории — ID и метаданные, бинарные копии на каждую версию не создаются. Перед физической очисткой файлов проверить ссылки из всех удерживаемых версий.
9. Очистка истории конкретной записи и всей истории — **явные пользовательские операции**; при включённой синхронизации они должны быть отражены общим детерминированным маркером очистки/эпохой, чтобы старые версии не вернулись из почты.

### 7.2. Корзина

Мягкое удаление (`deleted_at`) скрывает запись из обычных списков. Корзина общая, фильтруется по библиотекам, позволяет восстановить или удалить окончательно. Настраиваемое время: 7, 14, **30 по умолчанию**, 90 дней либо бессрочно. Очистка проводится при запуске/в доступные моменты; постоянного фона нет. После окончательного удаления остаётся техническое надгробие ID/HLC, чтобы запоздавшие данные не «воскресили» запись. Срок хранения надгробий в данной модели не ограничен.

## 8. Вложения и управление файлами

1. Оригиналы хранятся в приватном каталоге приложения, метаданные (ID, имя, MIME, размер, SHA-256, ссылка на запись) — в SQLite. Имена файлов в каталоге технические; миниатюры — локальный кэш.
2. **Общий порог автоматической синхронизации вложения** — 10 МБ по умолчанию, настраиваемый и синхронизируемый как обычная настройка. Проверяется размер отдельного файла до постановки в очередь.
3. До порога включительно: байты шифруются и передаются отдельно после метаданных, при необходимости кусками. Сверх порога: байты **не отправляются**, а синхронизируются только зашифрованные метаданные и подсказка об устройстве, где лежит файл.
4. При отсутствии локального содержимого отображается заглушка «`Видео.mp4 · 480 МБ · находится на устройстве “Телефон”`», а не сломанная ссылка. Хеш позволяет подтвердить вручную перенесённую копию.
5. Экран **«Крупные вложения»**: группировка библиотека → коллекция → запись, имя, размер, локальный статус/местонахождение, мультивыбор, экспорт копий в указанную папку, удаление. На Android — Storage Access Framework, на desktop — экспорт и открытие папки в проводнике/Finder.
6. Удаление связи из записи отличается от удаления локальных байтов. При удалении единственной известной копии показать предупреждение о необратимой потере; никакой автоматической бесшумной очистки единственной копии.
7. Отсутствующий/повреждённый файл фиксируется по наличию/хешу; выводится понятное состояние. При экспорте создаётся человекочитаемая структура, без переименования внутренних рабочих файлов.
8. Пользовательский архив БД включает **малые вложения**, крупные — метаданные и заглушки; крупные экспортируются отдельно. Этот порог относится и к импорту/экспорту по умолчанию, независимо от того, включена ли синхронизация.

## 9. Внешние действия и Android UX

- **«Добавить в календарь»** на Android открывает внешнюю форму календарного события через Intent с подготовленными параметрами. Пользователь подтверждает сохранение во внешнем приложении.
- **«Создать напоминание»** на Android вызывает доступный обработчик `ACTION_CREATE_REMINDER`; если его нет, предлагается создать событие календаря с оповещением либо показывается отсутствие обработчика.
- На Windows/macOS/Linux генерируется `.ics` и открывается ассоциированным приложением/диалогом. Изменение записи в нашей БД не обновляет уже созданное внешнее событие.
- Внутреннего планировщика, системных будильников и периодического уведомляющего фона **нет**.
- Android: системная кнопка «Назад», светлая/тёмная/системная тема, разрешения по запросу, Share текст/URL/файл во «Входящие» без второй формы сохранения, голосовой ввод средствами ОС, ярлыки библиотек, адаптивная клавиатура и формы. Целевые экраны, визуальные правила и поведение кнопки `+` — в [ui-specification.md](ui-specification.md).
- Действия карточки/списка: копирование значения, открытие URL, звонок, смена одного поля, создание связанной записи, вызов календаря/напоминаний. Отдельных Android-виджетов нет.

## 10. Локальный импорт/экспорт: отдельный механизм

**Экспорт БД и импорт БД — локальные пользовательские функции. Архив базы НИКОГДА автоматически не отправляется через SMTP/IMAP.** Почтовый транспорт передаёт только шифрованные дельты/контрольные пакеты; автоматического bootstrap-переноса полной БД по почте **нет**.

### 10.1. Экспорт

- Создаёт согласованный архив данных, схем, конфигураций, общих настроек, актуальных записей, истории последних 20 версий и малых вложений; крупные представлены метаданными. Указывает версии формата, `dataset_id`, HLC-метаданные, точку экспорта/состояние синхронизации; **не включает** пароль почты, секреты ОС, ключ группы, локальные очереди и `device_id` данной установки.
- Публичный открытый формат (manifest + версии JSON/SQLite-совместимых данных + файлы, хеши); опционально защита архива паролем с проверенной схемой.
- Android — сохранение через системный выбор папки/файла, desktop — стандартный диалог. Отдельно CSV экспорт/импорт конкретной коллекции (с настройкой соответствия полей, локали и предосмотром).

### 10.2. Импорт

- На чистой установке первый экран предлагает **«Создать новую базу»** либо **«Импортировать базу»**. Обе операции работают без интернета и синхронизации.
- При импорте в уже заполненную установку база **заменяется**, не сливается. Приложение предлагает предварительно выполнить **«Экспорт текущей базы»**. Отказ от экспорта не отменяет импорт: после явного подтверждения замены продолжается импорт. Проверка целостности, формата и достаточности свободного места обязательна.
- Замена атомарна на уровне стратегии staged import: импорт в отдельный каталог/БД, проверка, затем безопасная активация. Сбой не уничтожает исходную базу и не оставляет полузаменённое состояние.
- На импортирующем устройстве создаётся **новый `device_id`**. `dataset_id` сохраняется при восстановлении той же базы; пользователь может выбрать **«сделать независимой»**, тогда генерируется новый `dataset_id`, удаляются устаревшие транспортные курсоры и отключается прежняя синхронизация.
- Резервный архив должен быть пригоден для офлайн-восстановления и не требовать почты. Если после импорта включают синхронизацию с существующей группой, ключ передаётся отдельно по QR и осуществляется безопасное восстановление точки продолжения (см. §11). Нельзя просто копировать курсоры прежней установки как курсоры новой.

### 10.3. Новое устройство

1. На существующем устройстве вручную выполнить **«Экспорт БД»**.
2. Передать архив удобным пользователю каналом (локальная папка, USB, файловый перенос и т. п.). Само приложение не отправляет его почтой.
3. На новом устройстве выбрать **«Импортировать базу»**, получить данные и новый ID установки.
4. Если нужна синхронизация: настроить тот же транспорт и **передать ключ группы через QR** с доверенного устройства; установить точку продолжения обмена из согласованного состояния экспорта и последующих доступных дельт.
5. Если синхронизация не нужна — работать с импортированной базой локально; при желании сделать её независимой.

**Важное ограничение:** если архив устарел, а нужные письма/дельты больше недоступны, подключение к текущему состоянию не считается успешным; требуется более свежий архив. Просто наличие одинакового ящика и ключа не означает одинаковость данных.

## 11. Синхронизация (строго необязательная)

### 11.1. Идентификаторы и включение

- Новая независимая база получает случайный **`dataset_id`**, каждая установка — уникальный **`device_id`** с редактируемой подписью «Телефон», «ПК» и т. д. Один почтовый адрес не является идентификатором базы.
- При обычной офлайн-работе не требуется транспортных настроек/почтовых ключей. В интерфейсе синхронизация по умолчанию **выключена**. Первый запуск не должен предлагать обязательный почтовый вход.
- При включении пользователь задаёт выделенный SMTP/IMAP-ящик (рекомендуется отдельный), вводит учётные данные; для существующего набора данных **передаёт групповой криптоключ по QR** с доверенного устройства. Один адрес без ключа и идентичного `dataset_id` не объединяет базы.
- ID устройств нужны для HLC, выявления повторов, источников тяжёлых вложений и состояния обмена. Групповой ключ не хранится в открытом `app.sqlite` и не включается в обычный экспорт.
- При первичном включении синхронизации для ранее независимой базы фиксируется состояние/граница журнала для будущих дельт. Подключение двух уже независимо изменённых баз без импорта **не выполняется**.

### 11.2. Шифрование и почта

- До вызова нативного транспорта весь payload сериализуется детерминированно, сжимается при необходимости и шифруется **WebCrypto AES-256-GCM** с уникальным случайным 96-битным nonce на пакет, с аутентификацией служебного заголовка. Повторное использование nonce с тем же ключом запрещено. Использовать системный CSPRNG и проверенные API; никогда не реализовывать шифр вручную.
- Нативный SMTP/IMAP-адаптер передаёт **непрозрачные байты**, не знает ключа и пользовательских значений. Транспортная тема нейтральна; содержимое пакета не раскрывается серверу. Адреса, размеры, частота и время писем серверу видны — скрывать это обещанием нельзя.
- Ключ группы хранится в защищённом хранилище ОС; учётные данные почты — там же. Потеря всех устройств и ключа делает старые почтовые пакеты нечитаемыми; локальная резервная копия остаётся независимым способом восстановления данных.
- Защита от пакетов другого `dataset_id`, испорченных ciphertext, повторного номера/ID и подделанных метаданных обязательна. При отзыве устройства нужен новый групповой ключ для будущих пакетов; базовая реализация может осуществлять это как повторную настройку группы на оставшихся устройствах.
- Почтовое приложение **не удаляет письма**. Провайдер/пользователь может удалять их по своим правилам. Заполнение ящика и лимиты отправки выводятся как ошибка транспорта. На большой папке приём ведётся через курсоры IMAP/UIDVALIDITY, без повторного скачивания всей почты на каждом цикле.
- Ограничить размер шифрованного пакета ориентировочно 1–2 МБ, крупные малые вложения передавать кусками. Учитывать MIME/base64 overhead и реальные лимиты провайдера.

### 11.3. Правила репликации

1. Пакеты содержат **состояния синхронизируемых объектов**, их HLC, ID, а также **неизменяемые версии явных сохранений** и необходимые метаданные. Не синхронизировать результаты формул, FTS, черновики, локальные очереди, OS-пути и OS-секреты.
2. Для текущего состояния объекта **LWW по целому объекту**: больший `(HLC, tie-break)` побеждает. Два независимо изменённых поля одной записи не сливаются. Оба явно сохранённых варианта могут присутствовать в Top-20 истории.
3. Применение идемпотентно; повторы и перестановка пакетов не должны менять результат. Порядок прихода схем и данных допускает откладывание записей до доступности описаний.
4. В одной транзакции: сохранение объекта, `change_log`, версии и обновление соответствующих служебных курсоров. Не переотправлять удалённый объект из устаревшего пакета поверх более нового надгробия.
5. Пакеты имеют версию формата, ID набора, отправителя, монотонный номер отправителя, ID пакета и криптографическую аутентификацию. Устройство хранит принятые интервалы номеров и обрабатывает UIDVALIDITY/переезд IMAP-папки.
6. **Нет подтверждений ради удаления писем.** При пропуске номера приложение сначала проверяет доступные письма; если недостающие события недоступны и непротиворечивое продолжение не гарантируется — **останавливает синхронизацию, не заменяет базу автоматически**.
7. Не существует автоматического служебного «импорта полного дампа» через почту. Восстановление требует **локального архива** с другого устройства. Перед заменой текущей базы предложить её экспорт.
8. **Top-20 истории** применяется детерминированно, независимо от порядка доставки; при ручной очистке истории соответствующий маркер синхронизируется, чтобы не восстанавливать удалённые версии из старых писем.
9. Для синхронизируемых настроек действует тот же принцип идентичности и HLC; настройки внешней ОС/разрешений остаются локальными.

### 11.4. Расписание

- При запуске или возвращении приложения в активное состояние: один цикл приёма/отправки.
- Пока приложение активно: каждые **15 минут от последнего цикла** (интервал настраивается).
- По кнопке — немедленный цикл.
- При сворачивании — **попытка** отправки уже подготовленных пакетов; гарантии завершения нет. Не обещать отправку после принудительного закрытия.
- **Не отправлять письмо после каждого сохранения.** Пакеты накапливаются в локальном журнале/очереди; при неудачной передаче остаются до следующего доступного цикла.
- Доступна настройка **«Только вручную»**; режима «Только Wi-Fi» **нет**. Состояние сети — не общий пользовательский переключатель.
- При выключенной синхронизации приложение работает идентично в части локальных данных и UI.
- Статус: включена/выключена/приостановлена, последняя успешная дата, неотправленные пакеты, ошибка, имя устройства/ящик без показа секретов.

### 11.5. Долгое отсутствие и смена набора данных

**Предохранитель:** если с последнего полноценного успешного обмена прошло **90 дней** либо выявлен невосполнимый разрыв последовательности пакетов, синхронизация **приостанавливается**. Этот срок — пользовательская политика безопасности, а не математическое доказательство наличия/отсутствия всех сообщений. Сдвиг часов по порогу не проверять.

Пользователю доступны два простых пути, без слияния:

**A. Заменить локальную базу актуальным экспортом другого устройства:** предложить **«Экспортировать текущую базу перед заменой»**. При отказе от экспорта замена продолжается после явного подтверждения. Импорт staged/атомарный. Устройство получает корректную новую точку подключения/новый device ID; если архив не согласован с доступными дельтами, синхронизация остаётся отключённой до более свежего архива.

**B. Продолжить независимо:** отключить прежнюю синхронизацию, сгенерировать **новый `dataset_id`**, сохранить все локальные записи/вложения/историю и очистить только локальные протокольные состояния старой группы. Это **не** смена почтового адреса и не маскировка под новый `device_id` в прежней группе. Затем можно вести независимую базу офлайн либо отдельно настроить её транспорт.

Локальные несинхронизированные данные при A будут заменены и могут быть потеряны; это явно сообщается перед импортом. Автоматического слияния с актуальной базой нет.

### 11.6. Что синхронизируется

**Да:** библиотеки, коллекции и поля, записи и удаление, связанные ID, истории версий/маркер очистки, сводки, форма/карточка/список/быстрые формы, именованные профили отображения и пресеты создания, оформление и общие настройки (включая общий порог 10 МБ), метаданные файлов, небольшие файлы, имена устройств.

**Нет:** редакционные страховочные черновики, системные разрешения и пути, темы/масштаб или другие явно платформенные установки, пароли SMTP/IMAP, групповой ключ, local device ID как идентификатор этой установки, локальные очереди/курсоры, индексы/кэши/результаты формул.

## 12. Надёжность, миграции и безопасность

- Все миграции версионированы и транзакционны, если позволяют операции. До изменения системной схемы создаётся согласованный локальный бэкап. Использовать SQLite Backup API/VACUUM INTO/другой согласованный способ; **не копировать активный `.sqlite` без WAL-контекста**.
- Проверять целостность базы в разумные моменты, хеши вложений при обращении/экспорте; при ошибке поддерживать восстановление из локального архива.
- Импорт не уничтожает старую базу до успешной проверки новой. После краша во время экспорта/применения пакета/миграции должен оставаться предыдущий либо полностью новый согласованный результат.
- Общие настройки и типы полей мигрируют по версии схемы; приложение старой версии не применяет неподдерживаемые новые пакеты молча.
- Поиск, формульные кэши и миниатюры восстанавливаемы, cleanup осиротевших файлов учитывает связи из записей и удерживаемой истории. WAL checkpoint/очистка выполняются вне критической части UI.
- Локальные логи — без текстов «Секрет», ключей, паролей и полных payload пакетов; экран диагностики и экспорт отчёта доступны без облачной телеметрии.
- Android cloud backup пользовательских файлов приложения **выключен** (`allowBackup=false` и соответствующие правила data extraction для поддерживаемых Android); проверить итоговый merged manifest.
- UI-блокировка библиотеки не заменяет шифрование файла. Выгруженный незашифрованный архив может быть прочитан тем, кто получил файл; предлагается опциональная парольная защита экспорта.
- На desktop одна активная точка записи данных; второй запуск направляется в работающий процесс или управляемое второе окно, но не запускает независимый sync writer.

## 14. Тестовая инфраструктура и CI/CD

### 14.1. Локальный Windows dev-стенд

- `npm run dev:desktop` — запустить **Tauri + Rust SQLite** с реальным `app.sqlite` в изолированном dev-каталоге.
- `npm run test:unit` — бизнес-правила TypeScript и формулы.
- `npm run test:db` — реальная SQLite, запросы, миграции, индексы, FTS5.
- `npm run test:sync` — независимые экземпляры, упорядочивание, криптография, курсоры, долгая пауза.
- `npm run test:e2e` — автоматические UI-сценарии desktop/dev.
- `npm run test:all` — все локально доступные тесты, без требования Android Emulator для обычного запуска.
- `npm run build:desktop` — Windows x64 сборка. Это **контракт желаемых команд**, реализовать в `package.json`/скриптах репозитория.

Основные инструменты: Vitest для unit/integration/property-based tests, Playwright для подходящих UI E2E, Rust `cargo test` для адаптера, Android Instrumentation/Espresso или эквивалент для WebView/Capacitor. Библиотеки тестов допускается уточнять при внедрении без изменения продуктовых требований.

### 14.2. GitHub Actions

**Триггеры:** каждый `push`, каждый `pull_request`, вручную `workflow_dispatch`, релиз по git tag. Обязательные стадии: линтер/типизация → unit/DB/sync/property tests → сборки → публикация артефактов, только после успешных проверок. Linux, Windows и macOS jobs могут выполняться параллельно; репозиторий остаётся источником версий кода.

| CI job | Окружение | Результат |
|---|---|---|
| `checks` | Ubuntu / Windows | TypeScript, lint, unit, формулы, реальная SQLite, контракты |
| `sync-chaos` | Ubuntu | Случайные перестановки, дубли, потери, конфликты, Top-20, восстановление |
| `desktop-win-x64` | Windows x64 | Исполняемая сборка/установщик и Rust-тесты |
| `desktop-macos-arm64` | macOS ARM64 runner | `.app`/`.dmg`, Rust-тесты; подпись/нотарификация — отдельный релизный секретный этап |
| `desktop-linux-x64` | Ubuntu x64 | `.AppImage`, тесты native bridge |
| `android-apk` | Linux + Android SDK | APK для Android ARM64; вариант x86_64 для CI-эмулятора при необходимости |
| `android-emulator` | Linux + KVM emulator | Нативная SQLite, WebView, формы, Intent, Share, сохранение черновика, lifecycle |

**Android Emulator в GitHub Actions возможен.** Эмуляторный job можно сделать обязательным для PR/релизов, а на каждом push — запускать по мере доступного времени/ресурсов CI; обычные быстрые тесты обязательны на каждом push. Эмулятор проверяет API и модель жизненного цикла, но не гарантирует поведение энергосбережения конкретного производителя телефона. Необходимые реальные проверки перечислены отдельно.

**Безопасность CI:** ключи подписи, пароли и сертификаты только через GitHub Actions Secrets/защищённые environments; форки/PR не получают релизные секреты. Не публиковать настоящие пользовательские SQLite/почтовые данные в артефактах.

### 14.3. Обязательная матрица автотестов

- **Модель:** CRUD библиотек/коллекций/полей, обновление схемы, UUID, перенос из «Входящих», обратные связи, CSV и ошибок импорта.
- **SQLite:** JSON, FTS5, индексы выражений, сортировка русских строк, транзакции/rollback, миграции, целостность, WAL, staged import.
- **Формулы:** Decimal до 5 знаков, `NULL`, ноль, ошибки, циклы, многозначные/обратные агрегаты, `NOW()`, сортировка/фильтрация/группировка по локальному кэшу.
- **История:** сохранение/отмена/быстрые действия, дедупликация, Top-20 на двух и более экземплярах, очистка истории, запоздавшие версии.
- **Синхронизация:** HLC и LWW, дубли, перестановка, потери/пропуски, неверные/чужие пакеты, порча ciphertext, пропавший ключ, смена ящика, 90-дневная приостановка, независимая база, отсутствие автослияния.
- **Файлы:** SHA-256, порог 10 МБ, chunking, заглушки, экспорт группой, отсутствие локальной копии, потеря/повреждение, очистка с историческими ссылками.
- **UI:** мобильный конструктор, отдельные форма/карточка/список/сводка, именованные профили и пресеты, список 50 000 записей, быстрые действия, Share, внешние Intent; адаптивность и UX-критерии определены в [ui-specification.md](ui-specification.md).
- **Черновики:** только создание записи; debounce, обычное закрытие, сворачивание, убийство процесса в эмуляторе, восстановление при **повторном создании в соответствующей коллекции**, сохранение после «Закрыть», удаление **только после успешного «Сохранить»**, отсутствие в `records`/истории/синхронизации и невмешательство в редактирование.
- **Надёжность:** искусственное завершение во время миграции/импорта/отправки/применения пакета; отсутствие частичных состояний и утраты исходной базы.
- **Безопасность:** проверка `allowBackup=false` и merged manifest, запрет секретов в логах/FTS, secure credential storage, криптотест-векторы AES-GCM.
- **Производительность:** набор **≥50 000 записей, 20–30 полей, несколько тысяч связей**, измерения на dev/CI и Android emulator; не встраивать бенчмарки в пользовательский бинарник.

### 14.4. Что проверяется вручную

Работа реального телефона при принудительной выгрузке, энергосбережении OEM, сворачивании и попытке отправки; поведение различных приложений календаря/напоминаний; реальный SMTP/IMAP-провайдер (лимиты, авторизация, самописьма, переполнение); подпись и установка на macOS/Windows. Отсутствие физического телефона **не блокирует автоматизированные тесты Android**, но не отменяет эти последние ручные проверки перед повседневным использованием.

## 16. Очередность реализации

1. Создать репозиторий/монорепозиторий, React/Vite/Tauri/Capacitor, адаптеры, **настоящий SQLite на Windows**, подключить community SQLite на Android и проверить FTS/JSON на эмуляторе, настроить CI и четыре сборки.
2. Системные миграции, библиотеки/коллекции/fields/records JSON, UUID, индексы, FTS5, CSV, базовый мобильный конструктор формы/карточки/списка, тесты.
3. Входящие, Share, быстрые формы, связи и обратные связи, Decimal и формулы с агрегатами, производный формульный кэш, режимы списков и сводки.
4. Явное сохранение, страховочные черновики, Top-20 история, корзина, служебный HLC и транзакционный `change_log` — ещё **до реальной почтовой синхронизации**.
5. Вложения и их метаданные, локальный экспорт/импорт/staged replacement, независимые базы, управление большими файлами и исходная точка синхронизации в архивах.
6. Зашифрованные тестовые пакеты через файловый транспорт между независимыми экземплярами, property-based/chaos тесты, LWW/Top-20/потери/90 дней.
7. Опциональная почта: secure storage, QR-сопряжение, SMTP/IMAP через Kotlin/Rust, статусы/очереди, жизненный цикл при сворачивании. Проверить на Android Emulator, затем по возможности на устройстве.
8. Android Intents для календаря/напоминаний, desktop `.ics`, заключительная полировка UX и сборки Windows x64/macOS ARM64/Linux AppImage/Android APK.

**Уточнение к продолжению с v0.5.0:** не переигрывать завершённые этапы и не удалять существующие функции. Ближайший этап черновиков реализовать уже по новому §4.4 и F-06 аудита. Новые профили, пресеты, адаптивный конструктор и Markdown-возможности добавлять отдельными миграциями/коммитами по мере соответствующих этапов. Четыре универсальные dev/CI-библиотеки — «Питание», «Заметки», «База знаний», «Проекты/Задачи» — задают приёмочные сценарии, но не фиксированные продуктовые сущности и не встроенные пользовательские шаблоны. Описание тестового наполнения — [tests/fixtures/README.md](tests/fixtures/README.md).

Каждый этап должен завершаться **рабочей сборкой, автоматическими тестами и явно выполненными критериями приёмки**. Точный DDL, интерфейсы адаптеров и формат пакетов описываются **в исходниках, миграциях и тестах**, а не требуют ещё одной пользовательской концептуальной спецификации.

## 17. Обязательные правила для реализации

1. Целевую навигацию и визуальное поведение брать из [ui-specification.md](ui-specification.md); при неопределённой детали выбрать рациональный дизайн, **не менять** оговорённые границы данных, сохранения и синхронизации без отдельного решения.
2. Не объявлять синхронизацию успешной до проверки фактического применения; «письмо отправлено» и «данные получены другим устройством» — разные состояния.
3. Если сценарий не может быть проверен автоматически (например OEM battery killer), не подменять его пройденным тестом в эмуляторе; вести список ручной приёмки.
4. Обнаруженное несовместимое изменение схемы/протокола приводит к понятной ошибке и сохранению локальных данных, не к тихому сбросу.
5. Сохранение формы и страховочный черновик — разные операции. **Черновик никогда не участвует в пользовательской версии и синхронизации.**
6. История на всех синхронизированных устройствах сходится к одному Top-20 при одинаково доставленных событиях; старое текущее состояние не «воскресает» из запоздавшего письма.
7. Приоритет: **корректность данных > отсутствие фоновых задач > производительность > визуальная полировка**. Производительность достигается индексами, ограниченными выборками и кэшем, а не изменением пользовательских правил.
